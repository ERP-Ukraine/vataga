# Етап 14.1–14.2

Версія `17.0.2.26`.

## Доопрацювання зразка

`quality.check.sample.x_was_reworked` — Boolean із `default=False`,
`readonly=True`, `copy=False`. Позначається лише під час явного запису
візуального результату або фактичних показників відкритої перевірки
`in_process`, якщо наявне обчислення `sample_result` безпосередньо змінює
результат із `fail` на `pass`.

Обчислення допусків і `sample_result` не змінюються. Переходи
FAIL → pending → PASS або виправлення лише однієї з кількох невідповідностей
не вважаються безпосереднім переходом FAIL → PASS. Коли остання
невідповідність виправлена й весь зразок отримує PASS, створюється примітка
в Chatter перевірки:

> Статус зразка №1 змінено з FAIL на PASS після доопрацювання.

Позначка залишається після наступного FAIL. Повторний запис PASS не створює
повідомлення; новий фактичний цикл FAIL → PASS створює нову примітку.
Звичайне читання або повторне обчислення полів не змінює історію.

Захист діє в моделях для візуального результату та всіх типів комірок, а
існуючі RPC використовують ці самі записи. Клієнт не може встановити або
скинути позначку, підмінити її через `default_x_was_reworked` чи примусово
поставити PASS числовій комірці поза допуском. Перед внутрішніми записами
повторно перевіряються права та правила запису батьківської перевірки без
sudo. Нових ACL або шляхів підвищення привілеїв немає. Результати завершеної
перевірки залишаються захищеними наявними правилами.

## Актуальні невідповідності в Quality Alert

`_get_current_matrix_failure_data()` готує незалежний список словників:
`sample_number`, `parameter_name`, `actual_value`, `expected_value`,
`failure_reason`. Використовуються значення та норми snapshot перевірки,
а не змінені згодом налаштування пункту. Передаються тільки фактичні FAIL
комірки та негативний візуальний контроль; зразки PASS виключені.

Під час створення Alert із `in_process` список зберігається текстом у
`vataga_matrix_failure_snapshot` та додається до опису в екранованому HTML.
Опис інспектора і значення з контексту зберігаються. Працює також для
відкритої перевірки `quality_state='none'`. Після створення список є
незмінним знімком; повторне відкриття його не оновлює і не дублює текст.
У новому Alert після виправлення зразка цей зразок уже не потрапляє в список.
Для інших етапів збережено попередню умову додавання опису лише після FAIL.

Підготовка виконується до `super().create()`: право створення Alert не
потребує права його подальшого редагування. Рішення, призначення
затверджуючого, стадії та аудит Технічної ради не змінювалися.

## Статус x_sorting_parameter: інтеграція очікує перевірки бази

У доступних вихідних кодах інших модулів поле не знайдено. Наявність Studio
або іншого визначення в цільовій базі й тип поля не підтверджені.
**Цей модуль не створює `x_sorting_parameter` та не записує в нього.**
Незалежна підготовка даних і `vataga_matrix_failure_snapshot` вже працюють.
Після перевірки бази потрібен окремий адаптер до підтвердженого поля.

Адміністратор може виконати лише читання метаданих на тестовій базі:

```sh
odoo-bin shell -d TEST_DB < extra-addons/quality_vataga/tools/inspect_sorting_parameter.py
```

Потрібно підтвердити:

1. Модель `quality.alert`, технічне ім'я поля та точний тип (`text`, `html`,
   `char`, relation тощо), можливий ліміт довжини.
2. Власника: модуль або Studio (`ir.model.fields.state`, `modules`), щоб не
   додавати конфліктне визначення.
3. Ознаки `compute`, `inverse`, `related`, `store`, `readonly`, права доступу.
4. Призначення наявних значень і правило збереження ручного тексту. Лише
   після цього можна вибрати безпечний формат та спосіб запису адаптера.

## Перевірки після оновлення

На окремій базі з Odoo 17 Enterprise виконайте всю регресію модуля:

```sh
odoo-bin -d quality_stage14_test -u quality_vataga --stop-after-init \
  --test-enable --test-tags /quality_vataga --workers=0 --no-http
```

Новий `TestQualityStage14` перевіряє типи вимірювань, Chatter, повтори,
незмінність ознаки, прямі модельні записи, RPC, ACL, завершені перевірки,
актуальний брак, норми snapshot, HTML, контекстні значення, create-only доступ,
вхідний контроль та затвердження Технічної ради. Тести етапу 12 збережені.

Вручну перевірте всі чотири типи виправлень, точний текст і автора примітки,
позначку «Після доопрацювання», збереження ознаки при наступному FAIL та
заборону редагування завершеної перевірки. Створіть Alert із відкритої
перевірки: мають бути лише актуальні FAIL із нормами, збережена примітка
інспектора, жодних дублів при повторному відкритті. Повторіть затвердження
Технічної ради та звичайний вхідний контроль.

Історичні результати та Alert не перераховуються. Блокування виробництва,
робочих завдань, Scrap, Backorder та створення виробничих замовлень до цього
етапу не входять і не реалізовані.
