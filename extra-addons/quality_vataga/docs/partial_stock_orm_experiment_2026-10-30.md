# Этап 13.3: эксперимент на настоящем ORM и проект адаптера

Основа ERP-Ukraine/vataga: `026a1d811713ad6d9007fdf4a14cc820067a9f62`, только `staging`.
Версия модуля остаётся `17.0.2.62`: в этом изменении нет производственного
действия частичного выпуска. Требование **без Backorder** не заменено.

## 1. Окружение и границы доказательства

Эксперимент выполнен нативно на Windows, **без Docker**:

- Python 3.12.14; зависимости из официального `requirements.txt` Odoo 17.
- PostgreSQL 18.3, новый отдельный кластер `qunit-native-pg18-direct`,
  слушающий только `127.0.0.1:55433`, отдельный тестовый пользователь `qunit_probe`.
- Официальный Odoo Community 17.0, точный commit
  [`220f33cd7fda4a40af8372c33905d953d0b267dc`](https://github.com/odoo/odoo/commit/220f33cd7fda4a40af8372c33905d953d0b267dc).
- Настоящие `mrp`, `stock`, `stock_account`, `mrp_account`, FIFO и реальные SVL.
  Фикстура использует `manual_periodic`: автоматические бухгалтерские проводки
  этим запуском не проверяются.
- `run_quality_archive_tests.py` копирует неизменённые необходимые модели и тесты
  в временный технический addon, создаёт свою БД и удаляет её в `finally`.
  Существующие базы и серверы PostgreSQL не используются.
- В этом addon нет поддельных моделей QC, Alert или QUNIT. Он исследует нижний
  слой MRP/Stock, а не имитирует Enterprise Quality.

Для скорости только у этого одноразового кластера отключены `fsync`,
`synchronous_commit`, `full_page_writes`. Проверяется транзакционный откат,
а не восстановление после аварийного отключения питания.

Рабочие интервалы закрыты и созданы фикстурой явно: час работы при ставке 60,
а для отдельных проб — ещё 15 минут. Это тестовая подготовка ненулевой стоимости,
не доказательство штатного старта таймеров Enterprise Shop Floor.

## 3. Подтверждённые ограничения и непроверенные выводы

**Подтверждено на ORM:** сам открытый MO и реальный первый выпуск четырёх совместимы;
повторный вызов стандартного промежуточного проведения меняет старые связи;
неизменная стоимость WO повторяется в выходной стоимости. Списанное количество
компонентов в исходной фиксированной спецификации не удваивается.

**Установлено чтением quality_vataga, но не Enterprise-экспериментом:**
`NativeFactMoveLine.write()` должен отклонить повторную привязку защищённых строк;
`QualityUnitStockFact.create()` не допускает факт на открытом MO; полный валидатор
не допускает предшествующего выпуска. Их отключение не исправляет native defects.

Не проверены настоящие Enterprise QC/QCP, Alert, допуски, три WO с удержанным пятым,
lot, стоимость сотрудников, автоматические проводки и две параллельные сессии.
Community-тест без этих моделей не подтверждает сохранность их поведения.

## 4. Рекомендуемая архитектура: тот же открытый MO

Рекомендуется отдельный узкий серверный адаптер промежуточного проведения.
Stock, SVL и итоговую формулу цены продолжает выполнять Odoo. Ниже — конкретный
проект интеграции, **не уже выполненная реализация и не разрешение ослабить guards**.

### Операция и атомарность

1. Одно действие MO без ручного выбора определяет множество `U` годных,
   невыпущенных QUNIT. Неоднозначная идентичность/обязательный QCP — отказ.
   Все результаты, допуски, Alert и исполнения проверяются по каждому QUNIT.
2. Существующая `_lock_quality_transfer_scope()` и её revision write сериализуют
   release, QC и WO. Нужен одинаковый порядок блокировок: MO, затем evidence/WO.
3. В одном savepoint фиксируются `U`, уже проведённые строки/связи/SVL,
   новые ожидаемые количества, lot и company, состояние QC/WO, cost checkpoint.
4. Создаётся Python-local capability для точного cursor/MO, множества `U` и фаз
   проведения. RPC/context/default/write её не создают. Это отдельное назначение,
   не общий режим обхода из старого `_native_quality_complete()`.
5. `qty_producing` получает **накопленный** целевой выпуск: сначала 4, затем 5.
   Штатная `_set_qty_producing()` подготавливает только непроведённый расход.
   Уже отмеченное фактическое потребление нельзя молча уменьшать с 10 до 8.
   Несоответствие заявленному расходу блокирует действие с объяснением.
6. Вызывается штатный `_post_inventory(cancel_backorder=False)`.
   `_split_productions()` и `button_mark_done()` внутри частичной capability
   запрещены. После возврата обязательно проверяются точные движения/остаток
   и отсутствие дочерних MO.
7. Только новым проведённым строкам присваиваются факты QUNIT. Затем добавляются
   audit/checkpoint записи. При любом несовпадении откатывается всё проведение.
   Пустой набор новых QUNIT при повторе не вызывает Stock вообще.

### Сохранность старых строк без их изменения и восстановления

Новый override `stock.move.line.write()` действует только внутри capability:
для **точного** финального native `consume_line_ids` SET-команда отделяет строки,
проведённые до этого запроса, и вообще не передаёт их в `super().write()`.
Обычный вызов получает только новые строки. Дополнительно проверяются форма
команды, ID новых реально списанных компонентов и принадлежность MO/компании.

Все иные попытки изменения старых строк по-прежнему запрещены. Нельзя сначала
переписать историю, а затем восстановить её: это нарушит защиту и может вызвать
побочные эффекты. После native call старые строки/связи/SVL сравниваются со snapshot.
Наследование должно перехватить именно эту команду **до** существующего
`NativeFactMoveLine.write()`, не отключая его для остальных записей.

### Стоимость новых интервалов через штатный калькулятор

Нужен append-only audit checkpoint по WO, связанный с успешным release и настоящими
готовыми moves: накопленная штатная стоимость, уже учтённая предыдущими выпусками,
набор/отпечаток интервалов, ставки и остальные inputs установленного cost provider,
компания и валюта. Это не SVL и не таблица собственной оценки запасов.

Override `_cal_price()` только ограничивает фазу действия capability и вызывает
`super()`. Override `mrp.workorder._cal_cost()` внутри этой фазы:

```text
C_now   = super()._cal_cost()       # настоящий установленный калькулятор Odoo
C_delta = C_now - C_booked         # стоимость, ещё не включённая в выпуск
```

Вне этой операции метод возвращает обычную стоимость без изменений. После
успешного Stock записывается новый `C_booked=C_now` в той же транзакции.
`mrp_account._cal_price()` сам объединяет новый расход из настоящих SVL,
`C_delta`, штатный `extra_cost` и задаёт цену движения. Stock создаёт SVL как обычно.
Нельзя вручную записывать SVL, подменять `price_unit` своей формулой, обнулять
ставку WO или менять/удалять уже учтённые интервалы.

Условия безопасности для первой реализации:

- Старые интервалы, их loss/user/employee/workcenter и все стоимостные inputs
  неизменны. Смена ставки может дать положительный delta без новой работы:
  такой запрос отклоняется, а не капитализирует переоценку старых интервалов.
- Все интервалы закрыты; отрицательный/нечисловой delta — отказ. Проверяется,
  что сам native post не дописал расчётные интервалы через `_set_duration()`.
- Нельзя угадывать inputs стороннего Enterprise override. Поддерживаемая цепочка
  `_cal_cost()` подтверждается отдельными тестами; неизвестный provider блокируется.
- Первичная поддержка: один товар, целые Units, `none`/проверенный lot,
  обычный подтверждённый расход. Serial, byproducts, manual consumption и
  неподтверждённые варианты стоимости явно закрыты.

**Граница применимости delta:** вся накопленная до первого выпуска работа
попадает в стоимость первых четырёх, а пятое получает только новые затраты.
Это обеспечивает однократное включение общей стоимости, но не оставляет часть
старого труда в отдельной WIP-оценке пятого. Аналогично нельзя предполагать расход
8, если фактически для пяти уже использованы все 10 компонентов. Если требуется
распределять старые труд/компоненты между выпущенными QUNIT и удержанным WIP,
понадобится согласованная политика распределения; одной разности недостаточно.

### Продолжение работы пятого и окончательное завершение

`action_confirm_quality_native_units()` сейчас проверяет отсутствие stock facts
для всего набора до выделения новых исполнений. После выпуска четырёх это может
блокировать завершение WO2/WO3 для пятого. Нужна отдельная проверка **новых**
исполнений: уже выпущенные четыре допускаются только как чтение неизменной истории,
не как кандидаты повторной обработки. Автоматический выбор WO исключает их из
нового запуска. Исходные QC/Alert/QRUN не переписываются.

Полный путь 5/5 без предварительного частичного проведения сохраняется.
После частичного выпуска нужна отдельная ветка финализации: провести только
последний QUNIT тем же адаптером, затем закрыть MO без повторного проведения,
ценового расчёта, создания старых фактов или Backorder. Нельзя просто вызвать
старый `button_mark_done()`: он повторно входит в `_post_inventory()`.
Финализация всех уже проведённых moves тоже требует отдельной регрессии.

## 5. Альтернатива со штатным Backorder

Native путь: `button_mark_done()` → штатный wizard
`mrp.production.backorder.action_backorder()` → `_split_productions()` → Stock.
Родитель закрывается на 4, дочерний MO содержит 1. Это меняет исходное требование
и здесь не включается автоматически.

Идентичность QUNIT сохраняется существующей `quality.unit.continuation`,
QC/Alert/исполнения остаются на оригинальных объектах. Новые WO связываются с
исходными через `quality_native_parent_workorder_id`; чтение истории требует
проверенной серверной преемственности, а не копирования выполнений или QC.
`_quality_equivalent_workorder()` и repair-target уже используют эту схему.

Однако текущий legacy release не поддерживает автоматически целевой современный
маршрут 5/5/4: `_validate_quality_native_units()` требует legacy transfer control
и запрещает остаток с передачами. Штатное завершение закрывает WO, а split переносит
количества через `qty_reported_from_previous_wo` и может отменить уже выполненные
дочерние операции. Для пятого с историей WO2 необходим отдельный Enterprise-тест
эффективности допусков, Alert, ретеста и допуска к WO3. Утверждения «всё уже
сохраняется штатно» для QUNIT в этом отчёте нет.

| Критерий | Тот же открытый MO | Штатный Backorder |
| --- | --- | --- |
| Соответствие исходному требованию | Да | Нет, требуется отдельное решение |
| Нативные Stock/SVL | Сохраняются, но нужны два адаптера выше | Штатный путь разделения |
| Стоимость повторного выпуска | Нужен защищённый incremental checkpoint и неизменная база | Отдельные WO/интервалы дочернего MO |
| Старые связи готовых строк | Нужен узкий запрет повторной привязки | Родительские строки не входят в post дочернего MO |
| QUNIT/QC/Alert/исполнения | Остаются в исходном MO; корректируется выбор новых работ | Нужна преемственность к новому MO/WO и проверка истории пятого |
| Объём/сложность | Выше: checkpoint, guards, факты на открытом MO, финализация | Ниже по Stock/valuation; заметная работа по continuation целевого маршрута |
| Основной риск | Drift стоимости/интервалов и незаметная повторная финализация | Потеря применимости старых допусков/исполнений в новом MO |

## 6. Возможность без собственного расчёта себестоимости

Без собственного Stock/SVL engine и без повторения формулы native price —
**технически правдоподобно**: оставить Odoo расчёт cumulative cost, цены moves,
расхода и SVL; учитывать только уже капитализированную часть стоимости WO.
Без какого-либо дополнительного monetary checkpoint — нет: подтверждённый
native калькулятор не хранит, какая часть работы уже включена в прошлые выпуски.

Разность — дополнительный учёт включения затрат, не новый калькулятор ставок
или оценки запасов. Её корректность ограничена неизменной cost basis. Прототип
всего адаптера, сохранность QUNIT и безопасность финализации ещё не подтверждены;
поэтому производственная реализация и версия `.63` в этот коммит не входят.

## 7. План реализации и регрессионных тестов

1. **Отдельный MRP-прототип в одноразовом addon:** реальный Stock с узким фильтром
   `consume_line_ids`, persisted checkpoint и transaction-local cost scope.
   Проверить 4 → повтор → новые 15 минут → 1: старые связи/SVL/интервалы неизменны,
   суммарная стоимость компонентов 100 + работы 75 = 175, без дочернего MO.
2. **Отрицательные cost-тесты:** ставка/employee cost/loss/старые интервалы изменены,
   открытый таймер, неизвестный provider, отрицательный delta, overlapping интервалы,
   исключение после Stock и после checkpoint. Откат включает audit и checkpoints.
3. **Enterprise-интеграция без UI:** MO 5, WO1/WO2 обработали 5, WO3 только 4,
   смешанный QC 4 PASS + 1 FAIL; четыре реальные stock facts, у пятого нет факта.
   Pending/FAIL/Alert удерживают только соответствующий QUNIT; отсутствие QCP,
   идентичности, допусков или исполнения блокирует конкретный выпуск.
4. **Компоненты и valuation:** штатные 8+2; уже фактически использованные 10 не
   уменьшаются автоматически; tracked components, UoM rounding, реальные lot,
   FIFO/AVCO, автоматические сбалансированные проводки. Serial/byproducts/manual
   consumption до отдельных положительных тестов явно запрещены.
5. **Жизненный цикл:** повторный вызов без новых QUNIT, ремонт/ретест пятого,
   добавление только его исполнения WO3, выпуск одного, финализация без второго
   Stock, полное 5/5 без частичного выпуска, legacy `quality_transfer_controlled`,
   Scrap только по существующему отдельному решению, совместимость этапов 12/14.
6. **Обходы и конкуренция:** две настоящие транзакции на одном MO, повтор после
   serialization retry, RPC/context/default/direct write/direct Stock/create fact,
   ACL/компании и скрытые evidence; допускается один native posting и один набор фактов.
7. **Минимальное действие MO и Scheduled Action:** добавляются после предыдущих
   проверок. Автоматический Enterprise-сценарий создаёт временные MO/QC, вызывает
   именно рабочее действие, проверяет moves/SVL/QUNIT, откатывает данные и даёт
   одну запись `log()`. Только после успешных регрессий повышается версия.

Рекомендация: продолжать прототип **того же MO**, сохраняя исходное требование.
Backorder оставить отдельной альтернативой. Нынешний коммит подтверждает дефекты
и задаёт проверяемую архитектуру; готового безопасного выпуска QUNIT 4/5 пока нет.
