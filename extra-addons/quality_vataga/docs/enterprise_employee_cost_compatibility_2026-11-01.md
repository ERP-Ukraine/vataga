# Этап 13.3: Enterprise employee cost и аналитика WO

Основа: `staging`, `75e173b`. Версия остаётся **17.0.2.62**.
`main` и production не изменяются; Docker не используется.

**Рабочий Enterprise `_cal_cost()` остаётся заблокированным.** Новый код
распознаёт конкретный полученный исходник для аудита, но не добавляет его в
разрешённые производственные провайдеры. Реальная Enterprise ORM-база локально
недоступна. Подготовлен отдельный rollback-only staging-аудит.

## Установленная формула

Получен реальный метод staging:

```python
def _cal_cost(self):
    return super()._cal_cost() + sum(self.time_ids.mapped('total_cost'))
```

Провайдер: `odoo.addons.mrp_workorder.models.mrp_workorder.MrpProductionWorkcenterLine._cal_cost`,
файл `/mnt/enterprise-addons/mrp_workorder/models/mrp_workorder.py`, строка 805.
SHA-256: `71c4a9b3bfda60a38874a601ca26620730a9c121de75e030de7c13c593049d12`.
Этот hash воспроизведён из текста метода с исходным отступом и переводом строки.
Источник сохранён в `evidence/staging_enterprise_cal_cost_2026-11-01.txt`.

Community-база вычисляет стоимость WC по объединению интервалов даты/времени.
Enterprise добавляет стоимость **каждого** интервала сотрудника:
`employee_cost * duration / 60`. Для сотрудника используется hourly_cost,
для отсутствующего сотрудника — employee_costs_hour рабочего центра.
Duration берётся из настоящего `_compute_duration()` с
`loss_id._convert_to_duration()`, а не заменяется разностью дат в нашем коде.

При неизменных прежних входах разность двух накопленных стоимостей равна
новым затратам. Параллельные интервалы работников суммируются для труда,
а время WC объединяется. Поэтому простая сумма минут сотрудников не может
служить длительностью WC. Изменение двух ставок, сохраняющее общую сумму,
также не разрешает переписать уже учтённые затраты.

`_cal_price()` и распределение потерь не менялись. Запрет субподрядной ветки
сохранён. Материалы + оборудование + сотрудники должны войти в общий total;
правило терминального распределения остаётся `190 → 152 + 38`.

## Проверка и усиление checkpoint

Введён внутренний **basis version 2** в существующем JSON, без новых таблиц:

- идентичность WC и компании, ставка WC;
- каждый прежний интервал: даты, loss, WC, user, сохранённая duration,
  текущая/сохранённая категория потерь, компания и календарь WC;
- каждый employee interval: employee_id, фактическая employee_cost,
  duration, total_cost, loss_type и компания;
- текущие hourly_cost/компания использованных сотрудников и fallback WC;
- отпечатки цепочек `_cal_cost`, `get_duration`, WO/timer `_compute_duration`,
  преобразования duration, employee compute и методов аналитических записей.

Проверяются все прежние входы по отдельности. Новые сотрудники и интервалы
разрешены только при неизменности прежних данных и отсутствии наложения на
уже учтённое время. Старый неполный basis **не мигрируется автоматически**:
продолжение требует отдельного аудита. Старые записи не переписываются.

Для incremental выпуска basis сравнивается также после настоящего Stock.
При вставке самого checkpoint повторно проверяются его WO, фактическая
стоимость из текущей операции, полный набор timer IDs и неизменный basis.
Изменение duration в hook после Stock теперь тоже приводит к rollback.

Защита сохранённых вычисляемых полей расширена на `loss_type`: изменение
родительской категории не должно обходить `write()` таймера через пересчёт
related-поля. Сохраняются запреты изменения/удаления учтённых интервалов,
переназначения сотрудника, employee_cost и duration, а также блокировки
входных строк перед чтением. Отрицательная накопленная или ранее учтённая
стоимость отклоняется. Вычисление стоимости не запускается для уже
некорректного/устаревшего checkpoint.

## Аналитические записи

По Community-исходнику `mrp_account._compute_duration` обновляет аналитику
**после** вычисления duration. В предоставленной Enterprise-цепочке
`mrp_workorder_hr_account._compute_duration` вызывает
`_create_or_update_analytic_entry()` **до** `super()`.
Также Enterprise `mrp_workorder._compute_duration` передаёт дальше пустой
recordset для показанной ветки. Одного чтения этих методов недостаточно,
чтобы доказать актуальность amounts/unit_amount при изменении интервалов:
нужны реальная реализация аналитического helper и наблюдение ORM.

Новый отчёт показывает всю MRO и исходники `_create_or_update_analytic_entry`,
`_prepare_analytic_line_values`, `_compute_duration`, `get_duration`.
Аудит собирает значения и IDs аналитических строк по свежим счетам/ref MO
и всем связям WO с account.analytic.line. Скрытые связанные строки сначала
обнаруживаются, затем применяются обычные ACL/rules; доступа helper не выдаёт.
Связь с ранее существовавшей аналитической строкой считается ошибкой fixture.

Повторный пересчёт должен сохранять IDs, amount, unit_amount и связи.
Если повторный ручной вызов «исправляет» первоначально устаревшую аналитику,
аудит сообщает FAIL. После новой работы проверяется тот же эффект.
MO/WC distributions рассматриваются отдельно: их строки могут представлять
разные аналитические представления одной стоимости. Их общая сумма не
подменяет себестоимость изделия и не является бухгалтерской проводкой.

## Как выполнить staging-аудит

Доставить код и перезапустить Python-службу. Эта правка добавляет helper-методы
и внутренний JSON version, без новых таблиц. Для ранее не обновлённой схемы
`75e173b` отдельный upgrade quality_vataga всё ещё нужен перед испытанием потерь.
Версия модуля остаётся .62.

Временная Scheduled Action под системным администратором с обычными MRP, HR
и analytic правами: `scripts/enterprise_employee_cost_audit_scheduled_action.py`.
Внутри вызывается:

```python
report = env['mrp.production']._run_native_employee_cost_audit('odoo17-vataga-staging')
```

Helper требует точное имя базы и точный SHA/MRO полученного метода, отклоняет
неизвестные дополнительные `_cal_cost` и wrappers. Это **проверка источника для
аудита**, не разрешение производственного провайдера.

Создаются новые product/BOM/MO/WO, сотрудники со ставками **20/40**, WC **60**
и fallback **50**, аналитические счета в существующем плане и явные
синтетические закрытые интервалы. Существующие пользователи/сотрудники/настройки
не изменяются. Новый analytic plan не создаётся: его создание могло бы
изменить Python registry/DDL, чего savepoint не восстанавливает.

Подготовлены **14 вложенных сценариев**: повторная аналитика, новая работа,
перекрытие WC/сотрудников, fallback, native loss/calendar conversion,
user→employee mapping, ставки/компенсирующие ставки, назначение сотрудника,
duration, effective employee_cost, loss category, ошибка с rollback и
сохранённая блокировка рабочего провайдера. Mapping явно помечается как
неисполненный, если у текущего пользователя нет employee; пользователя
для прохождения этого теста не изменяют.

Результат каждого сценария и весь fixture **всегда откатываются**. Проверяются
аналитические значения после rollback и счётчики моделей. Возможны пропуски
номеров sequence. Весь fixture создаётся в отдельном cursor/transaction с
безусловным `rollback()` в `finally`, включая очистку postcommit callbacks.
Транзакция Scheduled Action получает только отчёт. Native методы
расчёта/аналитики не подменяются.

**Границы этого аудита:**

- не активирует PartialPosting или иной capability;
- не проводит Stock и не создаёт SVL/Scrap/GL;
- сравнивает реальный ORM cost/basis с захваченным эталоном **в памяти**;
- не создаёт фиктивный или настоящий капитализированный checkpoint;
- не доказывает исполнение price-phase delta, неизменяемого checkpoint в
  Enterprise и терминального потока 4 PASS + 1 FAIL.

Успешный ответ — `AUDIT_PASS`, `rollback=COMPLETE` со всеми рабочими флагами
`production_provider_authorized`, `stock_posting_exercised`,
`persisted_checkpoint_exercised`, `terminal_loss_flow_proven` = **False**.
Это не приёмка этапа 13.3. При отсутствии/несовпадении источника — FAIL,
`NO_FIXTURE_CREATED`.

После получения результата необходимо проверить исходники аналитического
helper и фактические строки. Затем решить допуск точного провайдера и выполнить
подготовленные настоящие Enterprise checkpoint/4+1 тесты и rollback-only
`production_loss_scheduled_action.py` для none/lot. До этого рабочая блокировка
сохраняется. Бухгалтерское отражение потерь при manual_periodic остаётся
явным `manual_periodic_pending`; проводка этой правкой не создаётся.
