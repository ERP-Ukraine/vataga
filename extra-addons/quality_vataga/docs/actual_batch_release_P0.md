# Частичный выпуск фактической партии — 17.0.2.63

## Исходное состояние и причина

Проверено 03.11.2026: локальная `staging` без изменений, HEAD и актуальная
удалённая `staging` — `1daa4d6f98ff4582944d0ca12bddf415f1e3df4e`.

`_quality_confirm_on_native_finish()` подтверждал обработку идентифицированных
трёх изделий, записывал количество и приостанавливал последнее рабочее задание.
Он намеренно не выполнял складской выпуск. Закрытие всего рабочего задания
требовало полного плана. `_quality_partial_universe()` требовал регистрации
всех пяти изделий; его отдельный механизм поэтапного выпуска сохраняет исходное
заказанное количество и не создаёт стандартный заказ на остаток.

## Изменение

Новый `models/quality_actual_batch_release.py` добавляет действие
`action_release_quality_actual_batch()` и кнопку «Випустити фактичну партію»
в производственном заказе. Кнопка появляется при частичном текущем количестве
и наличии поштучных фактов. Перед выпуском требуется явное подтверждение.

`_validate_quality_actual_batch()` проверяет точный фактический перечень,
его единственную зарегистрированную партию, компанию, товар, количество,
отсутствие предыдущего выпуска и выполнение всех операций. Ранее завершённая
операция без идентификаторов подтверждается её фактической обработкой ровно
этого количества. Последняя операция обязательно имеет ровно три записи
обработки именно этих изделий. История не дополняется задним числом.

Обязательные точки контроля, результаты, действующие допуски и удерживающие
сповіщення повторно проверяются общим `_validate_quality_batch_controls()`.
`_post_inventory()` повторяет валидацию непосредственно перед штатным складом,
в том числе после стандартного разделения заказа.

Завершение выполняет существующий `_native_quality_complete()` через
`button_mark_done()` и настоящий `mrp.production.backorder.action_backorder()`.
Odoo создаёт движения, списывает компоненты и рассчитывает стоимость штатными
методами. Ручных записей состояния, произведённого количества, движений или
оценки запасов в новом адаптере нет. Порядок стандартного завершения сверен с
[исходниками Odoo 17](https://github.com/odoo/odoo/blob/17.0/addons/mrp/models/mrp_production.py).

`_check_quality_actual_batch_stock()` проверяет завершение и фактическое
списание по каждому исходному движению. Ожидаемое списание фиксируется до
проведения: штатный `unit_factor` меняется после увеличения `qty_produced`.
`_record_standard_stock_facts()` связывает каждый из трёх идентификаторов с
реальным проведённым складским рядком и проверяет точное количество выпуска.
Контроль качества повторяется и после штатного завершения, до записи связей.

`native_backorder.py` получает Python-local признак `actual_batch`: только в
этом проверенном сценарии новый заказ не переводится в исторический защищённый
маршрут передач. Родитель, группа снабжения, спецификация и преемственность
рабочих заданий сохраняются стандартным мостом. Остаток 2 не получает изделий,
допусков или фиктивных записей обработки. Существующие режимы не изменены.

Весь вызов, включая склад, остаток, аудит и сообщение, находится в одном
savepoint. Повторное действие на завершённом заказе отклоняется. Используется
общая существующая блокировка производственного заказа. Контекст клиента
очищается; нужны одновременно роли производства и склада, обычные права записи
и доступ к основаниям качества. Новый код не добавляет `sudo()` или SQL.

## Фактические проверки

- 225 автономных тестов успешно на установленном Python 3.12; из них 23 новые
  проверки выполняют методы нового адаптера на автономных объектах.
- Компиляция Python всего модуля успешна; 40 XML разобраны; пути манифеста
  существуют; `git diff --check` без ошибок.
- Полный автономный набор содержит ещё 31 тест в трёх модулях, требующих `lxml`:
  `test_quality_alert_view_contract`, `test_quality_archive_contract`,
  `test_quality_interface_contract`. Установка зависимости выполнена в отдельный
  каталог вне репозитория, но sandbox-пользователь не имеет к нему доступа.
  Повторный запуск вне песочницы не был разрешён, поэтому эти 31 тест не входят
  в итоговый успешный прогон.
- Первый диагностический полный прогон на Python 3.13 выявил 12 отказов:
  10 контрольных AST-хешей используют формат Python до 3.13, один тест требовал
  старую версию манифеста, один запрещал кнопки в файле истории. Хеши не менялись:
  формат подтверждён Python 3.12. Ожидаемая версия обновлена; новая кнопка вынесена
  в отдельное представление, исходное представление истории сохранено.
- В `tests/test_quality_actual_batch_release.py` добавлены 15 Enterprise ORM
  методов, охватывающих P1 и N1–N14, реальный склад, списание, оценку,
  преемственность, отсутствие фиктивных изделий и откат после ошибок склада,
  создания остатка и записи складских фактов. **Они не выполнялись.**
- Community ORM и Enterprise ORM не запускались: в проверенных локальных Python
  окружениях нет Odoo/Enterprise. Найден работающий PostgreSQL; подключение к
  базам и создание инфраструктуры не выполнялись. Предыдущие 74 Community ORM
  теста не считаются результатом этого изменения.
- Docker не использовался. Staging и production не изменялись. Push не выполнен.

Автономные проверки не подтверждают склад, стоимость и Enterprise-интеграцию.
Код и локальный коммит подготовлены; главный критерий P0 требует следующего
ручного прогона и ORM-приёмки в доступном Enterprise-окружении.

## Ограничения

Новый путь разрешён только при обоих выключенных признаках обязательного
поштучного маршрута и исторических передач, без зависимостей рабочих заданий.
Нужен складируемый товар без партийного/серийного складского отслеживания,
целое количество в стандартных штуках, одна регистрация фактической партии
на последней операции, отсутствие предыдущих проведений, побочной продукции
и ручного потребления компонентов. Настройка создания заказа на остаток —
«Запитувати». Непредвиденные штатные мастера, включая предупреждение о
потреблении, приводят к отказу и откату; автоматически подтверждается только
ожидаемый мастер заказа на остаток.

Вся идентифицированная фактическая партия должна быть допущена. Метод не
выбирает автоматически два хороших изделия из трёх при одном удержанном.
`quality_unit_route_required=True` и старый частичный адаптер не открываются.
На обычные заказы новый обработчик стандартной кнопки не устанавливается.

## Пошаговая приёмка на staging

1. После отдельного разрешения на публикацию установить коммит на staging и
   обновить **только** `quality_vataga` до `17.0.2.63`. Войти пользователем с ролями
   производства, склада и доступом к контролю качества. Не менять исторический
   заказ CAB/MO/05144 для первичного теста.
2. В типе операции «Кабелі МН: Виробництво» проверить настройку создания заказа
   на остаток «Запитувати». Создать **новый** производственный заказ на
   `[SUB-CAB-0153] Кабель MD L_S_B - (М)` по существующей спецификации, план **5 шт.**
   Убедиться, что оба признака маршрута выключены, зависимости выключены,
   складское отслеживание товара отсутствует. Подтвердить заказ.
3. В штатном поле текущего изготовления установить **3**, план оставить **5**.
   Проверить наличие компонентов на складе для этих трёх изделий; сохранить
   исходные остатки готового товара и компонентов для сравнения.
4. Открыть «Нарізка», нажать «Почати», обработать 3, нажать «Виконано».
   Операция должна быть завершена с фактическим количеством **3**. Для неё не
   создавать искусственные идентификаторы или проверки.
5. Открыть «МК кабель MD L_S_B - (М)», начать работу и открыть обязательную
   проверку от `QCP00037 — МК Товар+РЦ`. Сформировать/обновить матрицу. Должно
   быть **3 образца**, а не 5. Для каждого отметить визуальный результат
   «Придатний»; если в текущей спецификации есть измерения — внести значения
   в допуске и выбрать требуемые средства измерения. Завершить контроль
   с результатом «Придатний». Проверить три идентификатора и **3 действующих
   подтверждённых допуска**, отсутствие удерживающих сповіщень.
6. На последней операции нажать «Виконано». Должны остаться три поштучных
   подтверждения, фактически обработано **3**, рабочий интервал закрыт.
   До следующего шага производственный заказ ещё не выпущен на склад.
7. Вернуться в производственный заказ, нажать **«Випустити фактичну партію»**
   и подтвердить диалог. После успешного действия исходный заказ и его рабочие
   задания должны быть завершены; план исходного заказа после штатного
   разделения — **3**, фактически выпущено — **3**.
8. Открыть складские движения исходного заказа. Готовый товар: проведено ровно
   **3 шт.** во внутреннюю локацию. В отчёте движений товара отфильтровать по
   новому номеру исходного заказа: одна фактическая партия, без второго выпуска.
   Сравнить доступный остаток готового товара с шагом 3: прирост **3 шт.**
9. На вкладке компонентов проверить реальные проведённые строки: количество
   по норме существующей спецификации на **3**, а не на 5. Для каждого компонента
   сравнить складской остаток до/после. На вкладке «Вироби / замовлення на залишок»
   проверить три изделия и ссылки на реальные складские строки. Для товара с
   оценкой запасов открыть соответствующие слои оценки; проверить количества,
   стоимость компонентов и штатно включённую стоимость операций.
10. Через штатную связь заказов на остаток открыть дочерний заказ. Количество
    **2 шт.**, тот же товар и спецификация, ссылка на исходный заказ и общая группа
    снабжения. Он не завершён, на склад по нему ничего не выпущено. Фактическая
    обработка и перенесённое количество его рабочих заданий — **0**. Новых
    идентификаторов для двух ещё не изготовленных изделий нет.
11. Повторный серверный вызов нового действия для завершённого исходного заказа
    должен дать сообщение, что повторный выпуск запрещён. Кнопка после
    завершения скрыта. Повторно проверить: склад всё ещё **+3**, списание прежнее,
    дочерний заказ только один на **2**.
12. На отдельных новых тестовых заказах повторить отрицательные случаи: один
    непридатный или непроверенный образец; отменённый допуск; открытое удерживающее
    сповіщення; нет подтверждения последней операции. Выпуск должен отклоняться
    целиком, без изменений складских остатков и без заказа на остаток. Для
    заказа с обязательным поштучным маршрутом новый путь должен оставаться
    недоступным, в том числе через прямой вызов действия.

Ошибки создания остатка, проведения склада и конкурентные изменения следует
дополнительно проверять ORM-сценариями на отдельной Enterprise тестовой базе:
`--test-tags /quality_vataga:TestQualityActualBatchRelease --stop-after-init`.
Этот селектор запускать штатным Odoo вашей тестовой установки, без Docker и
без production-базы.
