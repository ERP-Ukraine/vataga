# Фаза 2: штатные Work Orders и QUNIT — 17.0.2.58

База: `origin/staging`, `b0331a7`, версия `17.0.2.57`.
Статус: реализация для staging; **фаза 2 не принята до ручного теста на staging Enterprise**.

## Пользовательский процесс

Для новых маршрутов используются штатные `mrp.workorder.button_start(bypass=False)`,
`button_finish`, `button_done`, состояния, количества и `mrp.workcenter.productivity`.
Сигнатура `button_start(bypass=True)` сохранена; `bypass` передаётся в родительский
метод и не отключает серверный контроль предыдущих операций и QC.

Для новых маршрутов больше не показываются действия:

- «Передати допущені вироби»;
- «Прийняти передані вироби»;
- «Розпочати обробку виробів»;
- «Завершити обробку виробів»;
- «Зупинити обробку».

В карточке WO доступно поле «Вироби цієї операції». Полный состав собственной
идентифицированной QC или подтверждённого предыдущего выполнения применяется
автоматически. В остальных случаях уже зарегистрированные QUNIT выбираются явно.
Совпадение количеств не используется для угадывания идентичности. Новый Shop Floor
интерфейс не создаётся: его штатные RPC используют те же серверные проверки;
при неоднозначном составе нужно сохранить выбор в существующей карточке WO.

Штатное завершение создаёт подтверждённые `quality.unit.execution` со ссылками на
QUNIT, WO, оператора, время и использованные QC. `quality.unit.execution.batch`
используется как существующая неизменяемая группа фактов завершения; новый таймер
и записи передачи для неё не создаются. Частичный уникальный индекс по WO/QUNIT
сохранён. Повторное завершение не добавляет факты. Завершённые ранее операции без
поимённой идентификации не дополняются фиктивными фактами.

Проверки применяются также к `write(state='done')`, прямой записи выполненного
количества, созданию уже выполненного WO и созданию/переназначению productivity.
Изменение количества, маршрута и выбора изделий нельзя совмещать с завершением
в одном `write`, чтобы проверка не использовала прежние значения. Скрытые записи
QC и исполнения обнаруживаются до обычной проверки ACL и не исчезают из допуска.
Кнопки и запись фактов защищены savepoint, включая откат уже закрытого штатного
таймера при последующей ошибке.

## Граница частичного выполнения

Полная годная партия проходит штатные WO без send/receive. Незавершённая обязательная
QC, FAIL/Pending и открытый удерживающий Alert не разрешают продолжение.
Собственная незавершённая QC не запрещает начало обработки; будущая QC не блокирует
предыдущую операцию. Завершение операции требует её обязательных QC и действующих
автоматических допусков `.57`. При установленной идентичности предыдущие операции
должны быть завершены; при наличии поштучных фактов они должны охватывать эти QUNIT.

Сценарий 4 PASS + 1 FAIL **не реализован как частичное штатное закрытие WO**.
Штатный `button_finish` закрывает WO целиком и выбирает одно агрегатное количество;
`button_done` также устанавливает `done`. Это проверено по исходному коду
[Odoo 17 mrp_workorder.py](https://github.com/odoo/odoo/blob/17.0/addons/mrp/models/mrp_workorder.py).
Поэтому для нового маршрута оставлена блокировка завершения/продолжения с точной
зависимостью в ошибке: нужна Enterprise-проверка штатного частичного выполнения WO,
при которой незавершённый остаток сохраняется без складского выпуска и Backorder.
Выбор только четырёх PASS не превращается в завершение всех пяти. Новый движок
частичного выполнения в этой фазе не добавлен. Это ограничение обязательно проверить
и согласовать при ручной приёмке; оно не считается поддержанным сценарием.

## Совместимость и история

Сохранены `quality.unit.transfer`, события передач, `quality.unit.execution`,
`quality.unit.execution.batch`, QRUN/QUNIT, QC, допуски, ремонты, повторные проверки,
Alert и все ACL/правила компаний. Таблицы и архивные данные не удаляются.

`execution.transfer_id` стал необязательным, `controlled_unit_id` хранится прямо в
существующей колонке. Старые исполнения сохраняют свои прежние ссылки и значения;
новые штатные факты не нуждаются в искусственном transfer. Проверку обновления
реальной базы `.57` с историей нужно выполнить на staging Enterprise.

MO с уже установленным `quality_transfer_controlled` не разблокируются автоматически.
Для них оставлены прежние защищённые действия и история: переход активного старого
маршрута на новый процесс требует отдельного решения. Скрытие кнопок относится к
новым маршрутам. Автоидентификация и автоматические допуски `.57` не изменены.

Не изменены тела `mrp.production.button_mark_done`, `_post_inventory`, stock
`_action_done`, складское проведение, Backorder, Scrap, дозамовление, оценка и
списание компонентов. В существующий resolver QCP добавлена только приватная
область конкретной операции для WO; его поведение по умолчанию на складской границе
сохранено. Старые запреты складского проведения продолжают действовать.

## Обязательная проверка на staging Enterprise

На копии staging обновить модуль с `.57` до `.58`, затем выполнить ORM-регрессии
с тегами `quality_wo_phase2,quality_qc_phase1` и прежние наборы
`TestQualityUnitTransfer`, `TestQualityUnitExecution`, `TestQualityMatrixHold`,
`TestQualityProductionIdentity`, `TestQualityFullRelease`.
Для сценариев WO/QC требуется установленная интеграция Enterprise Work Orders;
пропуск тестов из-за отсутствия `quality_mrp_workorder` не считается успехом.

| Сценарий | Что проверять вручную / в ORM |
| --- | --- |
| Обычный MO, включая оператора без роли качества | Штатные start/finish; нет QRUN/QUNIT/transfer/facts |
| Три операции, QC только на третьей | Первые две без фиктивных QC и последующего дополнения фактами |
| Два PASS | Штатное завершение и следующий WO; по два факта на операцию; нет transfer |
| PASS + FAIL, PASS + Pending | FAIL/Pending не продвигается; остаток и таймер сохраняются при ошибке |
| Выбор только годной части | Понятная блокировка с зависимостью частичного WO; нет преждевременного `done` |
| Открытый Alert | Удержание сохраняется и после PASS повторной QC |
| Повторная QC без открытого удержания | Те же QUNIT; новый PASS заменяет прежний FAIL своего QCP для допуска |
| Повторное завершение | Факты, состав, результаты и аудит не дублируются и не переписываются |
| Штатное время | Один активный интервал пользователя; у новой группы фактов нет своего таймера |
| `button_start(bypass=True)` | Аргумент принят; незавершённый/неразрешённый предыдущий этап блокирует запуск |
| История `.57` | Все старые передачи/исполнения читаются; активированный старый MO остаётся защищён |
| ORM/RPC и атомарность | Чужой MO/QUNIT, поддельный контекст, прямые количества и инъекция ошибки после создания фактов не обходят запреты |

Проверить оба входа: существующую карточку WO и реальный Shop Floor.
Не выполнять складской выпуск/Backorder для подтверждения фазы 2.
Ручная приёмка на staging пока не выполнена; фаза 3 не начата.
