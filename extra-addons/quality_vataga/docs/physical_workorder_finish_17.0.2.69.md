# Завершение физической обработки — 17.0.2.69

## Причина и модель

Воспроизведение пользователя: CAB/MO/05154, SUB-CAB-0188, партия 0000137,
план 3, физически обработано 2. Данные этого MO разработкой не изменялись.

В `_quality_confirm_on_native_finish()` были смешаны три разрешения:
подтверждение физической работы, допуск после своей QC и завершение всего плана.
Условие `len(completed) == planned == current` и ветка `button_pending()`
оставляли последние 2/3 в `progress`, хотя факты обработки уже были сохранены.
Дополнительный `_check_quality_native_finish()` также требовал полный план.

Исследованные локальные исходники Odoo 17 (`addons/mrp/models`):

- `mrp.workorder.button_finish()` сначала вызывает `end_all()`, затем сохраняет
  `qty_produced or qty_producing or qty_production`, `state='done'`, даты и ставку.
  Уже подтверждённые 2 не превращаются в плановые 3.
- `button_done()` закрывает интервалы и состояние, но сам не задаёт количество;
  `action_mark_as_done()` вызывает `button_finish()` и обрабатывает длительность.
- WO `qty_produced` — обработанное операцией количество; это не складской выпуск MO.
- `state`, `qty_produced`, даты и календарная запись WO имеют `copy=False`.
- Native `_split_productions()` рассчитывает остаток каждой WO по фактическому
  обработанному количеству и создаёт новые WO со своими состояниями/историей.
- Все WO `done` могут перевести MO в `to_close`; это не `done` MO и не stock posting.

Используется **native `mrp.workorder.state='done'` на фактические 2**.
Отдельная постоянная система статусов не добавлена. План MO остаётся 3 до
складского split, MO `qty_produced=0`, не создаются третьи QUNIT/исполнения.

## Реализация и рефакторинг

Основной файл — `models/quality_native_workorder.py`:

1. `_quality_confirm_on_native_finish()` готовит физические факты без разрешения
   своей QC и без условия равенства плану. Для завершённой фактической партии
   больше не используется пауза как замена завершения.
2. `_finish_quality_native_work()` объединяет три публичных native-действия
   завершения. В обязательном маршруте они вызывают канонический native
   `button_finish()` после проверки фактической величины, оператора и истории.
3. Кратковременный Python `ContextVar` `_PHYSICAL_FINISH` ограничен одним WO,
   курсором и фактическим количеством. Он допускает только native-запись результата
   этой WO; не даёт разрешений на MO, Stock, PASS или допуски. RPC context его
   создать не может. `finally` всегда сбрасывает scope.
4. `write()` и `_check_quality_native_finish()` защищают native-переход:
   произвольная запись `done`, другого количества или изменение завершённого
   физического результата не подменяют native lifecycle.
5. В одной savepoint проверяется результат native-вызова: WO `done`, количество
   ровно фактическое, все таймеры закрыты. План MO, его складской факт и набор
   проведённых raw/finished moves должны остаться прежними. Неожиданный побочный
   эффект Enterprise fork вызывает отказ и откат всего подтверждения.
6. `button_start()` после блокировки MO отклоняет повторный запуск завершённой
   работы и параллельный запуск другим оператором. Enterprise callback
   `button_start(bypass=True)` для закрытой WO становится бездействующим вызовом,
   позволяющим завершить QC без нового интервала работы.
7. `_compute_quality_native_status()` показывает «Обробку завершено (2 з 3)»
   по настоящим native `done` и количеству, отдельно от результатов QC.
   Ранние native операции без QUNIT используют реальный агрегат; их история
   задним числом не создаётся.

При неоднозначной идентификации native WO закрывается на подтверждённые 2,
сохраняя `quality_native_identity_pending=True`, без выдуманных исполнений.
После явного сопоставления в QC оператор исходного интервала может той же
кнопкой подтверждения связать физический факт с изделиями без повторного запуска.
Одного совпадения количества недостаточно: нужны QRUN и точное соответствие
образцов текущей операции этим QUNIT. Противоречащая введённая матрица автоматически
не меняется. Пока сопоставление не разрешено, оба складских валидатора блокируют MO.

Сохранён отдельный старый сценарий обработки части **уже зарегистрированной**
изготовленной партии: если из текущего фактического задания 5 обработаны пока 4,
остаётся реальная незавершённая работа над пятым. Это не критерий `plan == current`:
обычные 2/3 с фактическим заданием 2 и двумя изделиями закрываются в `done`.
Исторические передачи и обычные MO без обязательного маршрута сохраняют свой путь.

Складской алгоритм 17.0.2.68 не заменялся. В
`quality_actual_batch_release.py` и `quality_full_release.py` добавлен явный отказ
при pending-идентификации. Native stock, audit расхода, `lot_producing_id`, реальные
stock.move.line, QUNIT stock facts и backorder продолжают работать через прежний
защищённый путь. Частичный `serial` остаётся закрытым.

XML `quality_native_workorder_views.xml` уточняет подсказку и позволяет завершить
сопоставление pending-идентификации уже закрытой WO существующей кнопкой.
Native статус в списке WO, на форме и на MO теперь действительно `done`.

## Проверки

Добавлен `test_quality_physical_finish_contract.py`: реальные отгруженные методы
подтверждения, write/start/finish, QC-переходов и статуса выполняются вместе
на явном native test double. Проверяются количества, ID исполнений, таймеры,
идемпотентность трёх кнопок, запрет запуска, конкуренция, неоднозначность и откат.

При заданном `ODOO17_SOURCE` дополнительный тест выполняет **сам метод
`MrpWorkorder.button_finish()` из локальных исходников Odoo**, а не его копию.
Это всё ещё тест без ORM, не подтверждение Enterprise MRO или PostgreSQL.

```powershell
$env:PYTHONPATH='output/test-deps312'
$env:ODOO17_SOURCE='<локальный каталог исходников Odoo 17>'
python extra-addons/quality_vataga/tests/run_portable_tests.py
```

Без `ODOO17_SOURCE` только проверка внешнего native-метода помечается SKIP.
Enterprise ORM тесты обновлены для `done` при 2/3 и дополнены проверкой всех трёх
кнопок, QC после native `done`, запрета повторного запуска, перезагрузки, выпуска
2/3 и чистого остатка. Тест с независимыми транзакциями проверяет stale snapshot
при физическом завершении и выпуске; commit собственных фикстур разрешён только
в одноразовой БД `qunit_enterprise_*`.

**Enterprise ORM, PostgreSQL, настоящий UI и работающий Odoo здесь не запускались.**

## Ручной UI-сценарий на новом MO

1. Проверить установленную версию `quality_vataga` **17.0.2.69**. Обновление модуля
   требуется для XML. CAB/MO/05154 оставить неизменным; создать новый тестовый MO.
2. Открыть **Виробництво → Операції → Виробничі замовлення → Створити**.
   Товар — **SUB-CAB-0188**, спецификация — соответствующая `2026: SUB-CAB-0188`,
   количество — **3 шт.**, компания и склад — обычные для этого маршрута.
   Нажать **Підтвердити**, при необходимости **Перевірити наявність**.
3. Убедиться, что включён **Обов’язковий поштучний маршрут**, исторические передачи
   не включены. Если режим не включился из действующей QCP, руководитель качества
   использует **Вимагати поштучний маршрут**. Производственный тип операции должен
   иметь backorder-политику **Запитувати**.
4. В MO до запуска операций задать фактическую величину **2** (`qty_producing`).
   План остаётся **3**. В **Партія/серійний номер** выбрать реальную совместимую
   партию либо один раз создать штатным **+**. Проверить товар и компанию партии.
5. На **Робочі завдання** открыть **нарізка 0188**, проверить текущую величину **2**,
   нажать **Почати**, затем **Підтвердити обробку / Завершити**. Ожидать `Завершено`
   (`done`), обработано **2**, остаток плана **1**, рабочий интервал закрыт.
6. Так же выполнить **обжимка 0188**. Если маршрут требует QC нарезки, сначала
   выполнить её и получить допуск. До допуска попытка **Почати** следующую
   операцию должна получить серверный отказ, несмотря на physical `done` предыдущей.
7. Открыть **перевірка кабеля 0188**, нажать **Почати**, затем
   **Підтвердити обробку / Завершити**, ещё не завершая QC.
   Ожидать **Завершено**, фактическое количество **2**, закрытый таймер.
   В описании результата — **«Обробку завершено (2 з 3)»**, отдельно ожидание QC.
8. Вернуться к списку WO и перезагрузить страницу. Все три операции должны быть
   `done` на 2. У завершённой операции нет активного рабочего таймера или
   повторного штатного старта. Через заранее открытую старую вкладку попытка
   **Почати** должна получить отказ без нового таймера и исполнения.
9. Проверить MO: план **3**, складской факт `qty_produced` **0**. Native MO может
   отображать **До закриття** (`to_close`), потому что WO закончены. Это ожидаемо:
   готовая продукция и компоненты ещё не проведены, backorder ещё не создан.
10. На последней WO открыть **Вироби та історія**: ровно **2** QUNIT и два факта
    `processed`. Если QUNIT появились только на последней операции, ранние WO
    сохраняют свои реальные агрегаты 2 без выдуманных исполнений.
11. Нажать **Переглянути перевірки якості операції**. Открыть QC этого нового MO.
    В **Показники** — два образца с теми же QUNIT; QC ещё не завершена, допусков
    нет. При необходимости **Ініціалізувати матрицю** без повторной регистрации.
12. Попытаться **Випустити фактичну партію**: получить отказ по QC/допускам.
    После отказа WO остаются `done` с количеством 2, исходный план 3,
    компонентов не списано, готового выпуска и backorder нет.
13. Заполнить реальные измерения, выбрать требуемые ЗВТ, установить обоим образцам
    **Придатний**, завершить положительным результатом (`do_pass`, локализованная
    кнопка **Придатний / Пройдено**). Ожидать PASS **2**, FAIL **0**, PENDING **0**,
    **Допущено 2**; проверить действующие записи на **Історія допусків**.
    При завершении QC новая обработка и новые таймеры появляться не должны.
14. На MO нажать **Випустити фактичну партію** и подтвердить диалог.
    Ожидать MO `done`, его native план после split **2**, факт **2**, исходные
    WO `done` на 2 и ровно один backorder с планом **1**.
15. На **Вироби / замовлення на залишок** проверить два stock fact по исходным QUNIT.
    Перейти по `move_line_id`: реальное движение `done`, товар и компания MO,
    правильный `lot_id`, источник — production, назначение — склад MO,
    сумма уникальных готовых строк **2**. Одну общую строку количества 2 не считать дважды.
16. На **Компоненти → детальні операції** проверить фактическое списание на два
    изделия: например, при норме 2/шт — **4**, а не 6. В истории перемещений
    отфильтровать исходный MO; в прослеживаемости партии должен быть выпуск **+2**.
17. Открыть остаток по имени из сообщения MO (обычно суффикс `-002`). План **1**,
    факт **0**, `qty_producing=0`, партия пустая, обязательный маршрут сохранён.
    WO новые, без старых исполнений и таймеров; QUNIT/QRUN, завершённой QC,
    допусков и stock facts исходного MO нет. Обязательные QCP относятся к новым WO.
18. Повторить выпуск из заранее открытой вкладки исходного MO. Ожидать отказ,
    без нового stock posting, расхода или второго backorder.
19. На отдельных новых MO повторить две отрицательные проверки: один FAIL;
    PASS с открытым удерживающим Alert. Физические WO должны оставаться `done`,
    выпуск — запрещён. Завершение работы не снимает Alert и не создаёт PASS/допуск.
20. На новом MO обработать **3/3**, выполнить QC **3 PASS**, нажать
    **Виготовити все**. Ожидать штатный выпуск **3**, без backorder.
21. На отдельном тестовом MO проверить обычный маршрут без обязательного
    поштучного режима: прежние native кнопки должны работать без новых требований.
22. Для конкуренции открыть одно незавершённое тестовое WO в двух сессиях.
    Одновременно подтвердить работу. Чужой активный таймер должен блокировать
    второго оператора; параллельный повтор того же пользователя может получить
    serialization/retry. После обновления итог строго один: WO `done` на **2**,
    два QUNIT/исполнения и один исходный набор закрытых интервалов.
23. Если идентификация неоднозначна, проверить `done` и количество **2** при
    сообщении об уточнении соответствия, без выдуманных исполнений.
    Введённую противоречивую матрицу не переписывать. После явного допустимого
    сопоставления QRUN/образцов двум изделиям исходный оператор использует ту же
    **Підтвердити обробку** для привязки факта. Само совпадение количества,
    повторное открытие формы или PASS другой партии не снимают блокировку выпуска.

Все шаги выполняются через UI. Выполнение серверного Python/SQL на staging
для этой приёмки не требуется и не предлагается.
