# Автоматизированная приёмка защит фактического выпуска

Разработка от `origin/staging` — `a145975e7d2bbea73bfb14745cb97d2014c9d371`,
проверено 04.11.2026. Изменения подготовлены локально и не опубликованы.
Версия модуля остаётся `17.0.2.63`: добавлены только методы Python и тесты,
без полей, XML и изменений механизма выпуска или себестоимости.

## Запуск

После отдельного разрешения на публикацию и загрузки нового Python-кода
на staging выполнить вручную в существующей Scheduled Action от системного
администратора с обычными ролями производства, склада и руководителя качества:

```python
report = env['mrp.production']._run_quality_actual_batch_acceptance_probe(
    expected_database='odoo17-vataga-staging'
)
raise Exception(str(report))
```

Готовый файл: `scripts/actual_batch_acceptance_scheduled_action.py`.
Он только вызывает метод и показывает отчёт. Исключение здесь намеренное:
Odoo покажет диагностический словарь в сообщении об ошибке. Оно не означает,
что отдельный сценарий получил FAIL: статусы находятся в самом отчёте.
Не требуется включать периодический запуск. Доступ к Odoo Shell/SSH не нужен.

Имя базы предоставлено пользователем по отдельной read-only проверке `env`.
Метод требует одновременно: `expected_database` в точности равен
`odoo17-vataga-staging`, фактическое имя базы совпадает с ним, пользователь
состоит в `base.group_system`. Иное имя, даже совпадающее с фактическим именем
другой базы, отклоняется до открытия диагностической транзакции.

## Безопасность и границы

Использован образец `quality_partial_release_probe.py`: в конце каждого
сценария безусловно вызывается `_ProbeRollback`, даже если результат PASS,
SKIP или FAIL. Исключение выходит из savepoint и откатывает сценарий.

Дополнительно каждый сценарий работает на собственном курсоре и отдельной
транзакции с тем же пользователем, без добавления привилегий. Курсор не
используется как контекстный менеджер, поскольку такой менеджер Odoo делает
commit при нормальном выходе. В `finally` всегда вызываются `rollback()` и
`close()`. Родительский курсор Scheduled Action не откатывается и не изменяется.

Это важно для отложенных уведомлений: rollback savepoint очищает pre-commit
состояние Odoo, но не весь post-commit список. Полный rollback отдельного
курсора очищает также post-commit callbacks; они не попадут в транзакцию
Scheduled Action. Порядок подтверждён по
[исходникам Odoo 17 sql_db.py](https://github.com/odoo/odoo/blob/17.0/odoo/sql_db.py).

Создаются собственные товары, категория, локация, тип производственной
операции с политикой остатка «Запитувати», рабочие центры, спецификация,
контрольная точка, команда и производственные заказы. Все они откатываются.
Существующий однокроковый склад текущей компании и штатный тип контроля
читаются как справочные данные; их настройки не изменяются. Новая точка
ограничена новым товаром, новым типом операции и новой конечной операцией.
Реальные заказы CAB/MO/05146-001, CAB/MO/05146-002, QC00331 и их товары
не читаются как тестовые основания и не изменяются.

Контекст создания отключает авто-подписку/отслеживание и немедленную отправку
писем; у исходного тестового заказа дополнительно проверяется отсутствие
получателей. Прогон предназначен для обычного серверного потока, не для потока
с флагом `testing`, в котором стандартная почта может отправляться синхронно.
Обнаруженные активные автоматизации `base.automation` на затрагиваемых моделях
дают SKIP до создания данных: их внешние эффекты нельзя отменить SQL-откатом.
Они не отключаются. Никакого monkeypatch в серверном методе нет.

После отката savepoint проверяются количества и отсутствие новых идентификаторов
по 44 моделям: товары/свойства, настройки собственного стенда, производство,
матрица и допуски, изделия, исполнения, факты склада, движения/строки/остатки,
слои оценки, почтовые сообщения и уведомления. Проверка выполняется в том же
repeatable-read snapshot, поэтому параллельная работа других пользователей
не вызывает ложное расхождение общих счётчиков. Ошибка проверки даёт FAIL и
`rollback=UNVERIFIED`; затем внешний `finally` всё равно откатывает и закрывает
курсор. COMPLETE присваивается только после успешной проверки.

Ограничение PostgreSQL: значения `nextval()` не возвращаются при rollback.
Прогон может оставить пропуски технических/документных последовательностей,
хотя тестовых документов, изделий, остатков и аудиторских фактов не останется.
Метод сообщает это в `limitations`; существующие последовательности не
перенастраиваются и не восстанавливаются вручную.

## Сценарии и статусы

| Код | Проверка серверного метода |
|---|---|
| P1 | Настоящий `action_release_quality_actual_batch()`: завершение 3 из 5, реальные складские строки на 3, компоненты 6 при норме 2, слои оценки по количеству, ровно один остаток 2, три складских факта |
| N1 | Один непридатный образец; ожидается точная ошибка его проверки |
| N2 | Один незаполненный образец, контроль не завершён; ожидается точная ошибка проверки |
| N3 | Один настоящий допуск отозван штатным `_revoke()`; ожидается точная ошибка отсутствия действующего допуска этого изделия |
| N4 | Настоящее открытое сповіщення привязано к одному образцу; подтверждается удержание и ожидается ошибка проверки этого изделия |
| N5 | С версии 17.0.2.67: предшествующая операция имеет подтверждённую фактическую обработку 3 изделий и остаётся `progress`; после QC ожидается успешный выпуск 3 и backorder 2 с обычным положительным аудитом склада |
| N6 | **SKIP**: публичная функция не принимает перечень изделий. Подмена принадлежности через штатные API сама запрещена; обходить неизменяемую идентификацию для staging-теста нельзя. Существующий изолированный ORM-тест проверяет чужие изделия в валидаторе |
| N7 | Сначала настоящий успешный выпуск, затем повторный вызов; ожидается точное сообщение о завершённом заказе, без второго выпуска/остатка |
| N8 | Текущее изготовление 5 при трёх зарегистрированных изделиях; ожидается ошибка соответствия количества |
| N12 | С версии 17.0.2.67: обязательный маршрут включается штатным действием; ожидается успешный выпуск фактической партии с сохранением требований контроля в backorder |
| N14 | Настоящий выпуск при контроле только на последней операции; ранее завершённая операция не получает фиктивных проверок или поштучной истории |

Негативный тест получает PASS только при ожидаемом `UserError`/`ValidationError`
с точным бизнес-сообщением и неизменном снимке производства, складских строк,
оценки, остатков, фактов изделий и дочерних заказов. `AccessError` всегда FAIL,
даже если текст совпал; `AttributeError`, ошибки настройки и неожиданные причины
отказа также FAIL. Диагностическая подготовка включает настоящий резервный
рабочий интервал из существующего probe для последней операции, если Enterprise
не запускает таймер автоматически. Это не проверка кнопок таймера Shop Floor.

SKIP возникает только при явно распознанном отсутствии предпосылки либо
небезопасном сценарии: нет обычных ролей, интеграции Enterprise с рабочими
заданиями, однокрокового склада, штатного типа pass/fail или полей назначения
контрольной точки; включены внешние автоматизации; поток находится в test mode;
либо сценарий требует запрещённой подмены идентичности (N6).

Поля результата: `scenarios`, `enterprise_orm`, `stage`, `error_type`, `reason`,
`release_action_attempted`, `rollback`, `persistent_test_records`,
`scheduled_scenarios`, `overall`. При успешной проверке отката число оставшихся
тестовых записей — 0; при неподтверждённой проверке — `None`, а не выдуманный 0.
`overall` получает FAIL при любом отказе, INCOMPLETE при SKIP/NOT RUN, PASS
только при полном успешно выполненном наборе. Поскольку серверный метод не
запускает ORM fault-injection/concurrency suite, общий результат после успешных
доступных сценариев будет **INCOMPLETE**, а не полная приёмка PASS.

## Отдельные Enterprise ORM-тесты

N9, N10, N11, N13 в отчёте всегда **NOT RUN**. В существующем
`tests/test_quality_actual_batch_release.py` остаются 15 методов: ошибки остатка,
склада и записи фактов, обычное производство, чужие изделия и повторный запрос.
Добавлены пять методов `tests/test_quality_actual_batch_acceptance.py`, которые
в изолированном ORM-процессе используют сам серверный стенд, проверяют все
доступные сценарии, откат реального склада после неожиданной ошибки и строгий
допуск к запуску. `unittest.mock.patch` находится только в тестовом файле.

Настоящая конкурентная приёмка N13 требует двух независимых транзакций и
доступного им committed стенда на отдельной одноразовой базе. Серверный probe
принципиально не делает commit; последовательный повторный вызов не выдаётся
за конкурентный тест. Этот конкурентный прогон не выполнен и не подтверждён.

После появления отдельного Enterprise runtime штатному Odoo test runner можно
передать оба селектора:

```text
--test-tags /quality_vataga:TestQualityActualBatchRelease,/quality_vataga:TestActualBatchAcceptanceProbe --stop-after-init
```

Использовать только отдельную временную тестовую базу. В Scheduled Action
не добавлять тестовые классы, mock-патчи, фикстуры или очистку данных.
