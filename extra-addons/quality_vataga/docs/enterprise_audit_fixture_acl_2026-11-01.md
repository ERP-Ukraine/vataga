# Этап 13.3: категории потерь в Enterprise-аудите

Основа: `origin/staging`, `68062df`. Версия **17.0.2.62** сохранена.

## Причина и исправление

Scheduled Action остановился при подготовке fixture: штатный ACL модели
`mrp.workcenter.productivity.loss.type` даёт MRP-пользователю только чтение.
MRP-менеджер также не получает create/write на эту модель. Это не результат
проверки Enterprise-формулы: сценарии ещё не выполнялись, источник совпал,
а транзакция откатилась.

`_native_employee_audit_setup()` и `native_loss_duration_conversion` теперь
создают свои категории через `_native_employee_audit_loss_type()`.
Только создание этих временных строк выполняется с `sudo()`; возвращаемый
recordset сразу получает исходный Environment пользователя. Создание причин,
MO/WO, сотрудников, таймеров, расчёт себестоимости и чтение аналитики
выполняются без дополнительного повышения прав.

Для `loss_category` разрешена ровно одна запись: изменение `loss_type` на
`performance` у категории, созданной этим же fixture. Проверяется список её
новых ID, курсор, пользователь, режим доступа и компания текущего аудита.
Существующие категории нельзя передать этому helper; поиск с sudo отсутствует.

Допуск временных категорий существует только внутри отдельного курсора
`_audit_fixture_transaction()`. Его `finally` всегда вызывает rollback,
очищающий postcommit callbacks, и сбрасывает локальный scope. Проверки внутри
аудита дополнительно используют savepoint и проверяют восстановление состояния
стоимости/аналитики. Запуск setup вне этой транзакции запрещён до создания
каких-либо записей. Пользователи, группы, ACL и существующие категории
не изменяются.

## Отчёт и повторный запуск

Сохранены все **14** сценариев. `exercised=False` означает **NOT_RUN**, а не
PASS. Пустой результат проверки означает FAIL. Отчёт содержит
`expected_checks`, `passed`, `failed`, `not_run`; отсутствующие сценарии
учитываются как невыполненные. `AUDIT_PASS` возможен только при 14 PASS.
Если у запускающего пользователя нет employee, сценарий native mapping
будет явно NOT_RUN и общий результат FAIL; существующий пользователь
не изменяется ради успешного отчёта.

После доставки кода и перезапуска Python-службы повторить **тот же**
`scripts/enterprise_employee_cost_audit_scheduled_action.py`. Его интерфейс
и имя staging-базы сохранены. Новых полей/таблиц эта правка не добавляет.
Ожидается `rollback=COMPLETE` и поимённый результат всех выполненных сценариев.

Контроль точного Enterprise source/MRO, блокировка производственного
провайдера, защита капитализированных интервалов и сбор аналитики сохранены.
Локальные тесты не являются реальным Enterprise-аудитом; его результат ещё
предстоит получить на `odoo17-vataga-staging`.

## Проверка

- 61 настоящий Community ORM-тест: прежние 57 и 4 регрессии ACL/rollback/отчёта.
- Те же 61 ORM-тест с установленным `mrp_subcontracting_account`.
- 198 автономных контрактов; Python/XML, import определений моделей и
  safe_eval-компиляция Scheduled Actions.
- Прежние реальные сценарии `140 + 35 = 175` и `190 = 152 + 38`, включая
  rollback, ограничения провайдеров и неизменяемость стоимости, сохранены.

Регрессии используют существующего обычного `base.user_admin`, у которого
штатный ACL действительно запрещает создание/изменение категорий. Проверены
обе категории fixture, обычные права у причин потерь, отказ изменению
существующей категории, вложенный rollback, rollback на успехе/исключении,
очистка postcommit callbacks, отказ вне своего курсора/пользователя и отсутствие
ложного PASS для пропущенной проверки. Расчёт стоимости не подменяется.
