# Полный выпуск 2/2 — staging, 17.0.2.55

Реализован пользовательский путь РЕАЛЬНОГО полного native MRP/Stock выпуска.
До ручной приёмки он требует отдельного разрешения администратора на одном
новом тестовом MO. Действие не симулирует склад и не отменяет прежние запреты.
Частичный публичный выпуск, экспериментальный posting engine и Scrap не открыты.

## Ручная приёмка через UI

1. Установить 17.0.2.55 на staging. Проверяющий оператор должен иметь роли
   Quality User, Manufacturing User, Inventory User. Администратор, разрешающий
   тест, дополнительно — Settings Administrator и Quality Manager.
2. Создать НОВЫЙ MO для `[SUB-CAB-0162]`, 2 шт. CAB/MO/05116 и QC00285 не
   использовать: QC уже закрыта без идентификации. Проверить BoM, доступность
   компонентов и реальное количество партии 2. Поддержаны хранимый товар,
   UoM «шт.», отсутствие lot/serial и побочных продуктов, автоматическое
   потребление компонентов; ограничения существующего native bridge сохранены.
3. Убедиться, что QCP00039 действительно назначена операции «Перевірка кабеля
   0162» и товару/компании/типу производства. Если на новом MO обязательный
   режим ещё не включён настройкой QCP, руководитель качества нажимает
   «Вимагати поштучний маршрут» только на этом MO; массово QCP не менять.
   Нарізку и обжимку выполнить и завершить штатно, без выдуманных QC.
4. Начать третью операцию. В её ОТКРЫТОЙ QC сначала выбрать «Ідентифікувати
   вироби»: новый QRUN, два реальных QUNIT, точное сопоставление двух образцов.
   Идентификация обязательно ПЕРЕД закрытием QC как PASS.
5. Заполнить оба образца и требуемые ЗВТ. Завершить QC с 2 PASS. Через существующую
   кнопку допуска явно подтвердить инспектором оба QUNIT. Открытых Alert нет.
6. Завершить третью WO и остановить все рабочие интервалы. Все три WO должны
   быть done с выполнением полной партии. MO ещё не выпущен на склад.
7. Администратором открыть этот новый MO и нажать «Дозволити тест повного
   випуску», подтвердить диалог. Разрешение действует только для этого MO и
   имени текущей базы; в копии с другим именем не действует. Оно не устанавливает
   quality_transfer_controlled искусственно и не отключает обязательный режим.
8. Проверяющим открыть «Повний випуск QUNIT». В одном небольшом мастере сверить
   ровно два идентификатора, отметить явное подтверждение и нажать
   «Випустити всю партію на склад». Это реальное проведение native MRP/Stock.
   При ошибке исправлять исходный контроль/допуск/операцию; не менять состояния
   через SQL, RPC-флаги или обходные кнопки. Ошибка откатывает всё проведение.
9. Проверить MO done, qty_produced=2, готовое движение done на 2, проведённые
   строки stock.move.line, +2 к внутреннему остатку, штатный расход компонентов,
   SVL по действующей оценке, два quality.unit.stock.fact с реальными строками.
   Backorder отсутствует при ask, always или never. Повтор кнопки показывает
   факты; повтор подтверждения прежнего мастера не создаёт движений или фактов.
10. В Settings → Technical → Automation → Scheduled Actions создать ОДНО временное
    действие Execute Python Code для модели Manufacturing Order. Вставить
    `scripts/full_release_scheduled_action.py`, заменить только `mo_name` новым
    номером MO и выполнить вручную до и после шага 8. Сравнить записи FULL-QUNIT
    в техническом журнале: после проведения `full_release_ok=True`, qty=2,
    2 уникальных QUNIT/факта, строки=2, backorders=[] и внутренний остаток +2.
    Это только чтение бизнес-данных и технический log(); задача ничего не проводит.
    После выпуска effectiveness допуска может стать False, поскольку допуск уже
    использован складским фактом; это не отменяет сохранённое подтверждение.

## Что проверяет сервер перед складом

Полный набор физических QUNIT, текущий MO/компания, отсутствие старого выпуска,
все WO/рабочие интервалы, реальные назначения QCP и сохранённые требования
QCP→операция→конкретный WO, завершённые обязательные QC/QRUN по каждому QUNIT,
чинные допуски, Alert и отсутствие уже выпущенных изделий. Требования QCP
сохраняются на MO и не исчезают при удалении QC или изменении настройки QCP.
Native bridge вызывается в savepoint под общей блокировкой MO; только Python-local
capability разрешает его штатные stock-вызовы. RPC-контекст не создаёт capability.

## Регрессии

Автономные контракты: `test_quality_full_release_contract.py`.
Реальные Enterprise ORM P1/N1–N12: `test_quality_full_release.py`, класс
`TestQualityFullRelease`; запускать только на disposable базе с test-tags
`/quality_vataga:TestQualityFullRelease`. Положительный тест использует тот же
публичный мастер, проверяет кванты, расход, SVL, факты и повторное подтверждение.
Настройки Backorder always/never проверяются для ПОЛНОЙ партии; частичный
публичный выпуск по-прежнему запрещён. Обычный MO сохраняет штатную кнопку.

87 автономных проверок прошли; Python/XML проверены. Фактическое проведение
P1 через staging UI и Enterprise ORM ещё не подтверждено. Этот файл — инструкция
для конкретной приёмки, а не утверждение о выполненном складском тесте.
