# Ручная read-only диагностика через Odoo 17 safe_eval

Полный код: [production_safe_eval_diagnostic.py](../scripts/production_safe_eval_diagnostic.py). Это отдельный скрипт, не shell-скрипты production_install_diagnostic.py/studio_preflight.py/odoo_preflight.py. Нет import/sudo/прямого SQL/create/write/unlink/изменения настроек, обходов sandbox, файлов или сети. Вывод только через UserError, без имен сотрудников/содержимого документов и текста исключений. При недоступном разделе печатается BLOCKED, а не вымышленный ноль. Все counts ограничены текущими ACL/rules/компаниями; даже административная сессия не доказывает полноту другой роли.

Ответственный администратор может вручную создать отдельное серверное действие «Execute Code», вставить полный код и запустить. Для штатной кнопки Run в технической форме можно выбрать модель `ir.actions.server`; контекстная привязка/website/расширение групп не нужны. Не нажимать Create Contextual Action, не менять права. Скрипт не привязан к record/records и не изменяет рабочие документы. Popup UserError с отчетом — ожидаемый результат, не ошибка установки. На production агентом ничего не создавалось и не запускалось.

Запланированное действие использует тот же eval context, но popup у cron отсутствует: UserError будет ошибкой в журнале задания. Не оставлять диагностику в периодическом cron и не подавлять исключение обходом ограничений. Предпочтителен ручной server action; запуск/сохранение самого задания и scheduler bookkeeping — отдельные штатные действия Odoo, скрипт настройки не пишет.

Вывод: база; статус/установленная и доступная версии addon и approvals/approvals_purchase/purchase/hr; metadata двух Studio-полей; Studio views approval.request (включая inactive); возможные vataga_* schema ownership конфликты; число purchase requests/items, статусы, заявки с сохраненными purchase_order_line_id, approved без текущей связи и старые manual-number requests. Старые = vataga_purchase_managed=False, если поле уже есть; иначе все существующие purchase-заявки. Это критерий происхождения workflow, не восстановленная дата установки. Отсутствие FK не доказывает, что закупки никогда не было.

Проверено реальной текущей сессией staging через отдельное TEST server action без контекстной привязки. Поля, версии, metadata и все агрегаты получены штатно. На production с отсутствующим addon запуск еще должен выполнить пользователь; staging не является его копией.

## Границы без shell/отдельного лицензированного runtime

- Нельзя надежно проверить файлы/commit/addons_path и исходники Enterprise, Python MRO/сигнатуры/AST-доказательство workflow_bridge и seller helper.
- Этот safe_eval скрипт не выполняет полное canonical XML наследование с кодом addon, проверку SQL-схемы/FK/индексов и замеры install/recompute. Для этого нужны shell/код и отдельное окружение; обходить ограничения safe_eval нельзя.
- SHA256-отпечатки исторических наборов/точное сравнение before-after предоставляет shell diagnostic. Counts safe_eval не заменяют проверку сохранности значений, backup и восстановление.
- Первая Install, повторный Upgrade, rollback и Enterprise ORM/HTTP-suite проверяются в отдельной лицензированной одноразовой БД; shared staging не деинсталлировать, production-базу не копировать.
- Конкурентные транзакции и ограничения других ролей не доказываются данным отчетом. Другие роли требуют собственных разрешенных проверок; их права ради диагностики не расширяются.
