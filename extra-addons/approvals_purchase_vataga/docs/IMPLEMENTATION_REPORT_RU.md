## Архитектура и ограничения безопасности

Подробности полей и методов — в [README](../README.md); полный перечень новых файлов — [FILES.txt](FILES.txt).

- `approval_request.py`: неизменяемый владелец/создатель, раздельные тема/номер/получатель, валидация отправки, standard super-chain, снимок после реального перехода в approved, защита категории, RFQ readiness/lock/marker.
- `approval_product_line.py`: условная обязательность описания; URL; снимок и история заполнения; create/write/unlink/One2many; сохранение согласованных вычисляемых полей; read/search/group/export через доступ к родителю; стандартный seller helper.
- `workflow_bridge.py`: структурная проверка **установленного исходника**, без копирования стандартного workflow. Только доказанная проверка пустого продукта может быть исключена. Декораторы, неизвестные конструкции и дополнительная логика сохраняются целиком. Unit-тестами проверена синтетическая цепочка до/после слоя, не реальный Enterprise workflow.
- `approval_category.py`: закрывает изменение типа/способа нумерации категории с закупочными заявками, включая скрытые от пользователя заявки. Ограниченное повышение прав служит только отказу и не раскрывает записи.
- `purchase_order_line.py`: при штатном удалении закупочной строки сохраняет техническое свидетельство существовавшей связи старой заявки. Это точечная операция по реально удаляемым строкам, а не миграция старых заявок.
- Мастер: закрытые проверки доступа и права закупщика выполняются заново при применении; продукт создается штатным ORM без повышения прав, только по явному нажатию.
- Представления: наследование исходных форм/tree/kanban; отдельные read-only виды реестра. Никакие стандартные правила/группы не переписываются, пользовательские роли не назначаются.
- URL: стандартный виджет расширен проверкой HTTP/HTTPS. Неверный URL черновика не становится активной ссылкой; сервер отклоняет его при отправке. Стандартный target `_blank` сохранен.

RFQ-marker и заполнение товара защищены одной блокировкой родителя в порядке ID. Кроме `SELECT ... FOR UPDATE`, меняется `vataga_lock_revision`: иначе при `REPEATABLE READ` второй клиент мог бы увидеть старое состояние дочерней строки. Native HTTP retry остается ответственным за повтор всей транзакции. `vataga_rfq_created` нельзя сбросить через RPC, импорт, `write`, defaults или возврат в черновик. Транзакционный savepoint окружает штатную RFQ-операцию и запись успешного маркера; ручного commit в методе нет.

Старым строкам не назначаются вымышленные признаки «не было товара» или «заполнили после». Их согласованные значения консервативно защищены, а неоднозначная старая отмененная заявка при возврате в черновик получает отдельный lock. Смена типа заявки, перенос строки и переключение способа нумерации требуют новой заявки; это описанные ограничения, а не скрытые сервисные способы снятия защиты.

## Перед приемкой и публикацией

Инструкция установки приведена в README. Сначала — preflight и полный прогон в одноразовой лицензированной тестовой БД, затем отдельное разрешение на публикацию/deployment/установку staging. Полный сценарий обязан проверить реальный MRO и регистрацию bridge; при неподтвержденной структуре исходный guard остается активным. Нельзя править статус/тип, использовать dummy product или выдавать роли для получения PASS.

Браузерная приемка: создать новую purchase заявку с существующим товаром и строкой без товара; сохранить; отправить; согласовать без нового товара; под закупщиком проверить freeze и однократное заполнение; явно создать товар при наличии стандартных прав; настроить подходящего поставщика; обновить форму; создать ЗНКП; повторить/параллельно вызвать операцию; отменить/удалить RFQ; проверить реестр, URL, parent access и компании. После этого проверить другие типы, существующие заявки, `approvals_sale_contract`, stock и Studio.

Основание для архитектуры доступа: [официальная документация Odoo 17 по безопасности](https://www.odoo.com/documentation/17.0/developer/reference/backend/security.html). Закупочные операции продолжают использовать стандартные [RFQ Odoo 17](https://www.odoo.com/documentation/17.0/applications/inventory_and_mrp/purchase/manage_deals/rfq.html) и фактические методы установленного `approvals_purchase`.
