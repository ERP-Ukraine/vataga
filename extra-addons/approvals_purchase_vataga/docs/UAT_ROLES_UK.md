# Короткий чекліст приймання за реальними ролями

Проводити лише на staging, на позначених TEST-VATAGA-APPROVALS документах. Не змінювати групи/паролі заради перевірки; не надсилати постачальникам, не підтверджувати замовлення або складські операції. Результат кожного пункту записувати PASS/FAIL/BLOCKED з роллю та посиланням.

| Роль | Що перевірити |
|---|---|
| Звичайний ініціатор | Створити заявку, додати наявний товар і рядок без товару з описом/HTTP(S) URL/дробовою кількістю, відправити. Власник визначений автоматично та незмінний. Чужі непогоджувані заявки не доступні через реєстр, пошук, групування, експорт і пряме відкриття. |
| Призначений погоджувач | Відкрити призначену чужу заявку та погодити штатною кнопкою. Minimum=2/обов'язковий погоджувач не дозволяють остаточного затвердження одним голосом; другий у послідовності чекає першого. Перевірити маршрут керівника. |
| Непризначений користувач | Сервер відхиляє погодження без повноважень; відсутність кнопки сама по собі не є повною перевіркою. Не використовувати адміністратора як доказ поведінки обмеженої ролі. |
| Перегляд усіх запитів | Загальний реєстр усіх purchase-категорій лише в дозволених компаніях; відбір і групування за командою/категорією; інші типи погоджень відсутні. |
| Закупівельник | За наявних прав відкрити «Заповнити товар» у readonly-таблиці, вибрати/створити товар, додати постачальника; погоджені опис/URL/кількість/одиниця не змінюються. Відмова при недостатніх catalog-ACL не повинна обходитися sudo або автоматичним наданням прав. |
| Закупівельник | Сформувати чернетку ЗНКП один раз; повторний запит/два клієнти не подвоюють закупівлю. Скасування або видалення тестового ЗНКП не дозволяє повторне формування. Контрольована конкуренція native RPC/SQL — окрема ізольована перевірка. |
| Кожна роль | Пошук/групування/експорт/пряме читання/перехід дотримуються правил документів і компаній. Кількість не редагується після відправлення. Інші типи погоджень працюють штатно. |

Перед остаточним прийманням: отримати production-метадані та узгодити відмінність автора, бізнес-ініціатора і співробітника-отримувача. Поточні поля .4 збережені сумісно, але ці бізнес-значення ще не підтверджені. Окремо погодити, чи призначені чужі заявки мають відображатися саме в загальному реєстрі для користувача без групи перегляду всіх запитів; доступ до них для погодження має зберігатися.

Поточні B04/B07/B09/C14/D11/E14/E16/E17/F09 залишаються BLOCKED до відповідних реальних перевірок. Адміністративна сесія не замінює перевірки ролей.
