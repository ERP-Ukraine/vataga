## Инициатор и получатель — BLOCKED до production metadata

В репозитории нет независимых ERP-UA полей инициатора/получателя approval.request. В текущем Show Fields staging перечислено 101 поле: присутствуют request_owner_id/res.users, partner_id/res.partner, date_confirmed/Datetime и только наши vataga_initiator_id/res.users, vataga_recipient_id/res.partner. В списке нет x_/Studio полей инициатора/получателя. Форма также показывает стандартную подтвержденную дату и ERP-UA contract/period расширения; отсутствие полей на staging не доказывает их отсутствие на production.

create_uid — фактический автор, он не доказывает бизнес-инициатора. res.partner не гарантирует сотрудника. Эти решения не считаются соответствующими уточненному смыслу; типы и накопленные значения сохранены до диагностики. Подсказки реестра обозначают временный характер. Новых дублирующих полей, автоматической миграции либо hr-зависимости нет.

В Community Odoo17 hr.employee содержит закрытые HR-данные; hr.employee.public имеет read ACL base.group_user и предназначен для общедоступной информации сотрудников. res.users не представляет сотрудников без аккаунта. Если production не содержит подходящих полей, предпочтительный кандидат — hr.employee.public с отдельной проверкой фактических record rules и доступа обычных ролей ERP-UA. Администраторский доступ текущей сессии не является доказательством для остальных. Окончательная связь, domain/компания и перенос старых партнеров требуют метаданных и согласования.

Ручная диагностика: scripts/production_field_diagnostic.py. Вставить в разрешенное серверное действие Execute Python Code и запустить вручную администратором; отчет отображается через UserError, копировать текст. Нет импорта, sudo, SQL, log или create/write/unlink/commit; читаются только поля, модели и представления, значения сотрудников и заявок не читаются. Native Odoo17 safe_eval компиляция проверена. Создание диагностического серверного действия выполняет сам пользователь; агент к production не подключается. Наличие state=base не приравнивается к штатному Enterprise происхождению: выводятся modules/XML IDs/наследования и state=manual для Studio/custom.

## Нумерация

Существующие APPR00007–9 видны в реестре staging. Native automated_sequence уже обслуживается стандартным create/super; сохраненный vataga_number фиксирует полученный native name. VPR применяется только к новым purchase-заявкам категории без automated_sequence. Удаление VPR сейчас оставило бы такие заявки без отдельного номера и затронуло бы контракт поиска/реестра. Последовательности, флаги рабочих категорий и старые номера не менялись. Безопасный будущий план: выбрать native sequence для новых категорий/заявок силами администратора; сохранить уже присвоенные APPR/VPR и исторический поиск; после подтверждения полного покрытия отдельно обсуждать прекращение VPR для новых документов. Автоматической перенумерации нет.

## Workflow, права и ORM

Подтвержденных оснований переписывать работающую архитектуру не найдено. workflow_bridge сохранен: AST разрешает пропуск только доказанного validation-only missing-product слоя; неизвестная структура fail-closed. Закрытый scope связан с cursor/uid/IDs; остальные уровни MRO и native super сохранены. Прямой вызов базового Approvals в обход MRO мог бы пропустить approvals_purchase_stock/sale_contract/ERP-UA расширения, поэтому не применяется. .3 реальный отрицательный тест minimum2/required при отсутствующем товаре остается применимым; sequence/manager и полная цепочка расширений требуют оставшихся runtime gates.

Серверные блокировки, compute-hook, snapshots, проверки approval.approver/One2many, RFQ savepoint/version-lock/tombstone не менялись. Три прежних PostgreSQL lock-проверки не подменяют детерминированное native RFQ перекрытие. .3 удаление TEST-ЗНКП и отказ повторного создания подтверждены. Разрешение редактировать после возврата в draft, ревизии, новые маршруты и статусы не добавлялись.

Реестр — исходные approval.product.line с purchase domain, без копий. `_search` ограничивает строки доступными родителями и активными компаниями, check_access_rule защищает прямое чтение/экспорт, переход проверяет обе модели. Закупочная группа не дает просмотра всех заявок или каталожных create-прав. Категория остается командой/отделом; отдельный «Проєкт» не добавляется.

Текущая серверная модель допускает назначенные документы в поиске исходной модели, сохраняя approval workflow; один лишь UI-фильтр «Мої заявки» не является границей безопасности.
