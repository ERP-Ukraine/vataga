## Read-only диагностика без установки

Скрипты не импортируют пакет нового addon, не создают/изменяют записи, не выполняют SQL/sudo/install/commit и не отправляют данные в сеть. Их можно прочитать и передать отдельно до размещения addon. Это **Odoo shell**, не safe_eval server action: импорты стандартных библиотек и lxml разрешены shell. Не создавать новые серверные действия на production ради запуска.

```sh
odoo shell -c /etc/odoo/odoo.conf -d odoo17-vataga --no-http < studio_preflight.py
odoo shell -c /etc/odoo/odoo.conf -d odoo17-vataga --no-http < odoo_preflight.py
odoo shell -c /etc/odoo/odoo.conf -d odoo17-vataga --no-http < production_install_diagnostic.py
```

Точные executable/config задает ответственный администратор по своему окружению; пароль в команды/отчеты не вставлять. Запуски читательские; скрипты в этой задаче **на production не выполнялись**. diagnostic печатает имена/состав metadata, XML ID/приоритеты/совпадение XML, числа XPath-matches полного combined arch, список других расширений, counts и SHA256 исторических наборов. Имена сотрудников/содержимое документов не выводятся. `load=None` читает идентификаторы связей без name_get; отпечатки не являются обезличенной копией БД для восстановления.

В baseline входят существующие purchase-заявки, их строки, approver rows, связанные закупки и все строки связанных закупок. Штатные native stored поля и два source-поля сравниваются до/после. Отпечатки детерминированы по ID и читаются batch500; лимит fingerprint50000 записей на модель дает BLOCKED_VOLUME и требует отдельного review объема. Скрипт работает в текущем разрешенном scope; одинаковые uid/company/lang и отсутствие параллельных изменений обязательны. Не выдавать более широкий доступ ради совпадения. Изменение hash требует разбора, а не автоматического исправления данных.

## Инициализация и исторические ограничения

- Custom init/pre_init/post_init/migration hooks отсутствуют. Нет массового вызова create/write/action_approve/action_create_purchase_orders по старым документам. Native Odoo `_auto_init` создает новые технические SQL-колонки/индексы/FK и ставит новые store-compute/related на пересчет существующих строк. Это реальные записи новых производных значений и потенциальная нагрузка; установка не называется «нулевым изменением БД».
- Source manual-поля не определены в Python/XML data, остаются manual с исходными XML IDs/значениями. Новые Many2one related используют тот же hr.employee, не ресемантизируют старые ID пользователей/контактов. Новые проекции `vataga_employee_*` штатно заполняются существующими employee-ID родителя. Compute этих проекций не меняет source-поле, сотрудника, owner или маршрут. При установке штатный installer имеет свой административный scope; compute_sudo=False не является доказательством поведения обычного пользователя — нужны S18/роли.
- Legacy vataga_initiator_id — новая аудиторская проекция create_uid при первой установке; vataga_recipient_id — новая пустая колонка на production, где addon раньше не было. Данных старого Vataga модуля там не предполагается. Уже существующие одноименные поля с посторонним типом/ownership — отдельный конфликт, который надо выявить до Install, не конвертировать автоматически.
- Старые native name/reference, owner, category/status, товары/описания/qty/UOM, approver rows, Studio employees и purchase links код не перенумеровывает и не восстанавливает догадками. Для native automated_sequence отображается прежний name; у старой ручной заявки новый VPR не назначается и номер собственного реестра может быть пустым. Согласованные снимки/даты/авторы заполнения старым строкам не выдумываются. Новые заявки получают текущую штатную/дополнительную нумерацию по существующей политике.
- Новые managed/approved_once/RFQ flags у старых записей не заполняются массово. Pending/approved/refused/cancel защищены реальным native статусом; сохраненная purchase_order_line_id дополнительно блокирует повторный RFQ и редактирование даже при пустом новом флаге. Удаление связанной закупочной строки после Install сохраняет техническое свидетельство перед очисткой FK. Старую отсутствовавшую позицию без подтвержденного снимка мастер не объявляет «отсутствовавшей при утверждении».
- **Исторический индикатор реестра в .6:** отдельный `vataga_rfq_exists` равен True по технической отметке ИЛИ любой штатной закупочной связи заявки, в том числе старой/частичной. Исходный `vataga_rfq_created` остается аудиторской отметкой и для старых связей может быть False; native FK блокирует повторное создание. Diagnostic после Install считает linked_requests_without_vataga_marker как ожидаемое различие с аудитом, а не ошибку проекции. Новая stored-колонка штатно пересчитывается; миграции отметок/дат/авторов нет.
- **Неустранимая без аудита неоднозначность:** если ЗНКП удален до установки и его FK уже очищен, новый модуль не может отличить «не создавался» от «создавался и удален». Текущий код не восстанавливает отсутствующие tombstones. Не формировать закупку повторно по таким production-заявкам без отдельной исторической сверки. Это ограничение первой установки, не закрытый staging-тест.
- Новое послабление description.required=False действует на SQL-колонку native строки; условная ORM-проверка сохраняет обязательность для nonpurchase. При первой установке не выполняется массовая проверка/исправление ранее существующих некорректных строк. Нестандартные ERP constraints/computes, противоречивые связи, архив/компании, сторонние defaults и некорректные manual metadata могут потребовать отдельного анализа. Фактический объем/время пересчетов production пока неизвестны.

## Безопасный откат

- При ошибке остановить запуск/повторные попытки Install, оставить writers закрытыми, сохранить traceback и install/deploy SHA. Не повторять Install, не удалять Studio-поля и не править служебные таблицы SQL для обхода ошибки.
- Ошибка registry/install не доказывает откат всех предшествующих модульных транзакций: загрузчик и платформа могут иметь отдельные commits. Код без модуля поверх частично обновленной БД не является достаточным планом восстановления.
- Штатный надежный rollback первой установки: ответственный администратор восстанавливает согласованные pre-install **БД + filestore + прежний код/config** в одно согласованное состояние при остановленных writers, затем запускает прежние workers и повторяет исходную read-only сверку. Не восстанавливать выборочные таблицы и не смешивать старую БД с новым filestore/кодом. Если после открытия окна уже появились новые рабочие операции, требуется отдельный план их сохранения; нельзя молча терять их восстановлением backup.
- **Не использовать Apps Uninstall как rollback на рабочей БД.** Он может удалить собственные технические данные/поля и повлиять на dependency graph; shared staging не деинсталлируется ради Install-теста. Не удалять/пересоздавать manual Studio-поля или чужие views, не откатывать чужие commits.
- Возвращать доступ к writers только после совпадения исходных fingerprints/counts/Studio metadata, нормального старого workflow и разрешения ответственного администратора. Сам rollback и восстановление на production в этой задаче не выполнялись.

До закрытия отдельного first-install runtime/production preflight/ролей модуль готов для контролируемой демонстрации на staging; **рабочая production-приемка не подтверждена**.
