# Интеграция подтвержденных Studio-полей / 17.0.1.0.5

Единый источник: approval.request.x_studio_iniciation и x_studio_who_recived, оба optional stored editable Many2one(hr.employee). Имена, comodel, XML ID, state=manual, значения production не изменяются кодом. Модуль не объявляет эти поля в Python/XML data и не берет их метаданные под управление. На staging пользователь разрешил создать только два отсутствующих manual-поля: они созданы через Technical→Models→approval.request→Fields до публикации .5;103 поля вместо101, каждое имя встречается один раз. Значения production не копировались.

Manifest добавляет явную зависимость hr (уже установлен на staging); зависимости studio_customization нет. Связь определяется техническим именем поля, а не ID ir.model.fields или Studio XML ID. На production существующие XML ID остаются studio_customization.many2one_approval_re_ef8bf1c2-68d7-47eb-89dc-a425fb65a32e и studio_customization.many2one_approval_re_b86112ec-6382-46d9-a609-3c26ea6ed9cd. На staging воспроизведен контракт manual-полей без копирования внешнего Studio-модуля/представлений.

## Registry и порядок загрузки

Реальный Odoo17 BaseModel._setup_base добавляет manual-поля через ir.model.fields._add_manual_fields до field.prepare_setup и настройки related. Поэтому оба поля должны существовать **до первого импорта нового addon/Apps Install**. Для уже установленного модуля (staging) это означает до замены Python-кода и обычного перезапуска. На production модуль пока не установлен: простое размещение файлов не равно регистрации его моделей, но обязательные source-поля проверяются заранее. Не следует рассчитывать на post_init_hook или создание полей во время Apps Install/Upgrade: related уже будут загружаться раньше. Если поле отсутствует или имеет другой тип/comodel, deployment BLOCKED; нельзя удалять или пересоздавать существующее поле для обхода ошибки.

В .5 две новые сохраняемые проекции строки: vataga_employee_initiator_id и vataga_employee_recipient_id, related к указанным source-полям, compute_sudo=False. Поиск, группировки и стандартный экспорт используют именно эти hr.employee-проекции. Старые vataga_initiator_id/res.users и vataga_recipient_id/res.partner остаются с прежними SQL-колонками/связями, помечены legacy и отсутствуют в актуальных формах/колонках/поисковых полях. Получатель legacy становится техническим readonly; значения не копируются в новые source-поля. Числовые ID не интерпретируются как ID сотрудников.

Нет автоматической миграции:0 сотрудников присвоено из legacy. Ни create_uid, ни контакт не гарантируют однозначной связи со штатным сотрудником, включая несколько компаний, архив и сотрудников без аккаунта. Старые источники доступны для отдельной контролируемой сверки/экспорта под прежними правами. Новая пустая бизнес-проекция старой заявки означает отсутствие подтвержденного сотрудника, а не потерю прежнего контакта.

## Форма и Studio priority160

Получен полный фактический XML production: form вставляет оба поля после category_id с invisible="category_id not in [9, 12]"; tree вставляет create_date/date_start/date_end/partner_id после name и recipient(show)/initiator(hide) после request_owner_id. Полные payload сохранены только как tests/fixtures, не manifest data. Regression использует их целиком с native Odoo17 inheritance, реальной полной архитектурой staging и текущим helper. Для purchase итоговая видимость False независимо от category_id; для nonpurchase исходное условие [9,12] остается без изменений. Это числа исторического чужого Studio XML, не условия бизнес-логики addon. Наши XPath меняют атрибуты/добавляют отдельные поля, не удаляют name/request_owner_id/category_id; стандартное approval.request tree не переопределяется. [Заключительная проверка](FINAL_STUDIO_COMPATIBILITY_17_0_1_0_5_RU.md) разделяет XML PASS и оставшийся S19 runtime BLOCKED.

Наследование основной формы больше не вставляет legacy-поля. Cooperative ApprovalRequest._get_view сначала получает полностью собранную native/ERP/Studio архитектуру, затем копирует ее для локальной обработки. Если source-поле уже присутствует, оно сохраняется на месте; если отсутствует, добавляется только для purchase. Зависимости от Studio form XML ID нет. Поэтому priority160 и tree99 не вызывают повторной вставки. Изменение возвращаемого arch не записывает чужие представления.

Для purchase source-поля необязательны, видимы и readonly по vataga_lines_locked; сервер write блокирует оба реквизита по той же политике после отправки/approval/возврата вdraft. Для других типов исходные readonly/required/invisible/domain Studio сохраняются. Новые fallback-элементы скрыты на других типах. Сохраняются нативные группы/ACL. Локальные тесты проверяют отсутствие дубликатов при наличии обоих/одного/ни одного Studio-поля и сохранение непокупочного поведения. Это не является исполнением полного production Studio XML.

## Сотрудники и права

Новые назначения purchase проверяются через hr.employee.public без sudo: сотрудник активен, виден текущему пользователю и принадлежит компании заявки либо общей компании. Если заявка общая, действуют нативные правила разрешенных компаний. Для выбора используются штатные hr.employee-поля: реальный Odoo17 делегирует публичный поиск/имя/fetch в hr.employee.public для пользователей без HR-read, не раскрывая закрытые поля. Наш код не предоставляет HR-права и не меняет ACL. Выбранный сотрудник не становится владельцем или согласующим, не получает отдельного доступа. Связь с res.users для выбора не требуется.

Архивный сотрудник не допускается как новое назначение. Архивирование ранее выбранного сотрудника не очищает значения/историю; отображение старых имен остается под штатными правилами доступа. Реальные отрицательные роли, межкомпанейские ограничения и публичный fallback в ERP-UA требуют отдельной приемки; администраторская сессия не доказывает их PASS.

«Скасовано» реализовано отдельным registry badge на базе native BadgeField. Только наш tree использует виджет; request_status='cancel', стандартная selection/глобальные переводы и другие формы не изменяются. Экспорт технического статуса сохраняет нативный контракт.

## Будущий порядок установки на production — только после отдельного разрешения

1. На production модуль NOT FOUND: предстоит **первая Apps Install**, а не Upgrade с .4. Согласовать окно и backup БД+filestore/прежнего кода/config, проверить восстановление; не переносить базу на staging. Сохранить исходные Studio-поля/представления и их внешние ID. [Отдельный pre-main/Install/rollback чек-лист](PRODUCTION_FIRST_INSTALL_CHECKLIST_RU.md) обязателен.
2. В работающем окружении до первого импорта/Install выполнить read-only scripts/studio_preflight.py, scripts/odoo_preflight.py и scripts/production_install_diagnostic.py через Odoo shell. Они не импортируют новый addon и не устанавливают/изменяют записи. Сверить source-поля/публичную HR-модель, полную фактическую production-цепочку views/MRO и baseline исторических документов. Staging давно не синхронизировался и не заменяет эту проверку.
3. На production поля уже есть: **не создавать, не переопределять и не переименовывать их**. Если в иной тестовой базе их нет, сначала штатно создать эти два manual-поля с теми же техническими именами/типами, readonly=False/required=False/store=True и без default/compute/related; сохранить модель, перезагрузить и повторить preflight. Не подменять relation существующего поля.
4. Только после PASS preflight, отдельного разрешения и проверки Install в лицензированном одноразовом окружении разместить код .5 и выполнить **первую Apps Install approvals_purchase_vataga** с согласованной конфигурацией/БД; не обновлять все приложения. Не удалять studio_customization. Перезапустить штатные workers. В этом чате production deployment не выполняется, first-install runtime BLOCKED.
5. Проверить Installed17.0.1.0.5, metadata обоих source-полей и прежние XML ID, одну пару реквизитов в форме, новую пару колонок, исторические legacy-значения и существующие рабочие документы без записи. Сотрудников в старые заявки автоматически не назначать.
6. Только после успешного Install повторить **Apps Upgrade** этого модуля и те же проверки без дубликатов. Сверить native fingerprints, Studio IDs, исторические RFQ-связи и особенности незаполненных новых audit flags; выполнить реальный ролевой чек-лист. При ошибке следовать согласованному restore DB+filestore+code, не Uninstall и не SQL-обходу.

Данные диагностики и staging не доказывают полной совместимости с production. Исходники Enterprise локально недоступны, TransactionCase/HttpCase на общей staging не запускаются. [Фактическая приемка .5](UAT_17_0_1_0_5_RU.md): два Apps Upgrade без конфликтов,103 поля и одна пара source widgets, legacy сохранены по контрольному native CSV,17 PASS/0 FAIL/2 BLOCKED нового этапа.
