# Закупочні затвердження Vataga

Odoo 17 Enterprise / ERP-UA, версия **17.0.1.0.0**. Зависимости: `approvals`, `approvals_purchase`, `purchase`.

**Статус: кандидат для проверки в лицензированном Enterprise-окружении. Полная приемка НЕ завершена.** Исходники Enterprise локально недоступны, модуль на staging не установлен. Нельзя считать локальные unit/SQL-проверки подтверждением работы стандартного согласования и создания ЗНКП. См. [отчет и матрицу требований](docs/IMPLEMENTATION_REPORT_RU.md).

Актуальные результаты дополнительного review, исправления, риски и самостоятельно принятые бизнес-решения: [CODE_REVIEW_RU.md](docs/CODE_REVIEW_RU.md). Он уточняет первоначальный отчет.

## Назначение

Модуль наследует существующие `approval.request` и `approval.product.line`. Применяется к `approval_type == 'purchase'` без привязки к категории, ее названию или ID. Новых маршрутов, статусов и копий заявок нет. `approvals_purchase_stock` поддерживается как установленное расширение: его таблица и склад не заменяются; ручные изменения любых полей согласованной строки блокируются.

В черновике допускаются незаполненные строки. При отправке проверяются товары, описание и HTTP/HTTPS URL для отсутствующих товаров, положительное конечное количество и совместимость выбранных единиц. Пустая единица существующего товара заполняется из карточки до отправки. Ошибки перечисляют заявку и номера строк. Владелец и фактический создатель новой закупочной заявки устанавливаются сервером; пользовательские значения и defaults не могут их подменить.

После отправки строки доступны только для чтения. После окончательного стандартного согласования сервер фиксирует согласованное состояние. Закупщик с **существующим** доступом к заявке может один раз заполнить исходно отсутствовавший товар через кнопку «Заповнити товар» или эквивалентный проверяемый ORM-вызов. Описание, URL, количество и уже согласованная единица сохраняются. Неизвестная история старых строк не восстанавливается предположениями.

Мастер предлагает существующий товар либо явное создание нового. Открытие мастера ничего не создает. Новый товар получает описание, URL, `purchase_ok` и компанию заявки. Связь и признак происхождения сохраняются в исходной строке. Создание/редактирование карточек и поставщиков использует штатные права: сама группа `purchase.group_purchase_user` обычно дает чтение товаров, но не их создание. Дополнительные права существующим пользователям модуль не выдает.

## Стандартное согласование

`action_confirm`, `action_approve`, отказ, отмена, отзыв и возврат в черновик продолжают вызывать стандартную цепочку `super()`.

`workflow_bridge.py` проверяет **фактически установленный** метод `approvals_purchase.action_approve()` через AST. Допустим только доказанно чистый слой: проверка типа `purchase`, проверка пустого `product_id`, исключение с текстом и точный кооперативный вызов `super`. Учитываются singleton-поведение, аргументы и их значения по умолчанию. Декораторы, обертки, дополнительные проверки прав, уведомления или иные действия не допускаются для исключения слоя.

При подтвержденной структуре на этом конкретном классе устанавливается ограниченная обертка. Только внутри закрытой области нашего `action_approve` она пропускает доказанную проверку товара и продолжает MRO непосредственно за этим слоем. Наследники **до и после** него сохраняются. Область привязана к курсору, пользователю и ID записей; JSON/RPC-контекст ее не включает. Остальной workflow, права согласующих, required/minimum/sequence/manager, активности и история остаются в штатном коде. Прямой записи `request_status = 'approved'`, подмены типа, фиктивных товаров и `sudo()` для согласования нет.

**Если структура не подтверждена, исходный метод сохраняется целиком.** Если он запрещает отсутствующий товар, такой сценарий останется заблокированным до анализа конкретных исходников и проверки адаптера. Это обязательная граница совместимости, а не успешно пройденный тест. Одних метаданных staging недостаточно для утверждения совместимости.

Замораживание согласованных значений учитывает также последующие compute-запуски из карточки товара: используется проверенный базовый ORM hook `_compute_field_value`, без предположений об именах Enterprise compute/onchange методов. Для незакупочных и редактируемых строк сохранен штатный расчет. Этот hook требует отдельного Enterprise ORM-прогона.

Прямые записи статуса и конфигурации `approval.approver` после отправки запрещены, включая команды One2many и JSON-контекст. Стандартные действия заявки передают закрытый серверный capability и сохраняют исходные ACL/rules. Изменение собственных согласований не требует дополнительного права редактировать родителя только ради технического снимка. Ввод readonly compute/related полей заявки через create/write/defaults также проверяется сервером.

## ЗНКП и конкуренция

Готовность вычисляется без хранения, поэтому перечитывание формы учитывает измененных поставщиков. Проверяются штатный `_get_seller_id()` при подтвержденной сигнатуре/типе результата и допустимые поставщики по компании, варианту, датам, количеству и единице. При отсутствии helper применяется проверенный `_select_seller()` продукта. Неподтвержденный контракт дает понятный отказ; `seller_ids` сам по себе готовность не доказывает.

`action_create_purchase_orders()` повторяет серверные проверки и вызывает существующий стандартный метод. Группировка, расширения ERP-UA, цены, валюты, налоги и использование существующих черновиков остаются в нем.

Перед операцией заявки блокируются в порядке ID. Дополнительно меняется техническая версия строки родителя: при `REPEATABLE READ` это заставляет конфликтующего клиента повторить транзакцию, даже когда первый клиент изменил только дочернюю строку. Успешная отметка ЗНКП записывается **после** стандартной операции, проверки всех связей и в том же savepoint. Ошибка откатывает связи, документы и отметку; ручного `commit()` нет.

Обновление ORM-кеша при блокировке исключает поля и обратные связи, защищенные активным штатным compute. Это предотвращает удаление еще не сохраненного результата вычисления согласующих.

Повторный вызов, отмена и удаление ЗНКП не разрешают повторное создание. Для старых заявок учитываются существующие `purchase_order_line_id`. При удалении связанных закупочных строк точечная техническая отметка сохраняет свидетельство обработки до очистки FK. Повторный вызов заканчивается понятным отказом и не увеличивает количество в стандартных строках закупки.

## Реестр и доступ

Меню «Реєстр заявок на закупівлю» использует исходную `approval.product.line`; одна позиция — одна строка. Представления предназначены для чтения, с переходом к заявке, поиском, фильтрами и группировками. Серверный `_search` накладывает SQL-подзапрос штатно доступных родительских заявок в активных компаниях, сохраняя исходные правила самих строк. Прямые чтение/экспорт дополнительно проверяют родителя через `check_access_rule`. Группировка и поиск используют тот же ограниченный запрос. Для формирования реестра `sudo()` нет.

Стандартные владельцы, назначенные согласующие и существующая группа просмотра всех заявок сохраняют свой доступ. Группа закупщиков сама по себе не дает просмотра чужих заявок. Единственная новая ACL — доступ закупщиков к собственному transient-мастеру. Повторная проверка строки и родителя выполняется при каждом действии мастера.

Ограниченное `sudo()` используется для запрета изменения типа уже используемой категории, технического свидетельства перед удалением связанного ЗНКП и записи технического снимка/необратимого lock согласованной заявки. Последняя операция не меняет статус: снимок после согласования создается только после успешного возврата из штатного workflow. Бизнес-данные пользователю не раскрываются, native workflow и его проверки выполняются с исходными правами.

Стандартные Datetime-периоды сохраняют время без усечения. Если ERP-UA определяет исходные поля как Date, проекция использует полночь UTC; исходные поля заявки не изменяются. Отображение в локальном часовом поясе следует проверить на staging. Группы доступа исходных периодов переносятся на проекции при setup модели.

Полный список файлов: [FILES.txt](docs/FILES.txt). Структура: `models/` — наследование и ORM-защита; `wizard/` — заполнение; `views/` — формы/реестр; `security/` — только ACL мастера; `data/` — последовательность; `static/src/` — URL; `tests/` — Enterprise и переносимые тесты; `scripts/` — проверки и preflight.

В категориях с автоматической последовательностью используется стандартный номер из `name`, а тема вводится отдельно. Для ручной темы номер новых заявок формирует `VPR/<год>/<номер>`. Существующий `reference` не переименовывается в номер заявки. Старые данные и история не мигрируются; известный стандартный номер может отображаться без добавления вымышленного нового номера.

## Установка и проверки

1. До установки прочитать отчет, выполнить read-only preflight в **лицензированной тестовой** среде и сопоставить MRO, поля, XML ID, права и supplier helper. Скрипт ничего не устанавливает:

   ```sh
   odoo shell -c /etc/odoo/odoo.conf -d VATAGA_ENTERPRISE_TEST --no-http < extra-addons/approvals_purchase_vataga/scripts/odoo_preflight.py
   ```

2. В отдельной одноразовой Enterprise-БД со штатными Enterprise и ERP-UA исходниками установить и проверить модуль. Базу production не копировать:

   ```sh
   odoo -c /etc/odoo/odoo.conf -d VATAGA_ENTERPRISE_TEST -i approvals_purchase_vataga --test-enable --test-tags /approvals_purchase_vataga --stop-after-init --workers=0
   ```

3. После исходной установки проверить повторное обновление в той же **одноразовой тестовой** БД, включая совместную установку `approvals_sale_contract` и `approvals_purchase_stock`, если они доступны. Полный двухклиентный RFQ-тест — `scripts/test_rfq_rpc_concurrency.py`; он принимает только localhost и требует свежую согласованную тестовую заявку, логин тестового закупщика и переменные `VATAGA_TEST_URL/DB/LOGIN/PASSWORD/REQUEST_ID`. Не использовать рабочие учетные записи и общую staging-БД для автоматических TransactionCase-тестов.

4. Только после отдельного разрешения пользователя выполнить публикацию ветки, deployment на staging и установку через Apps. `main`, production и workflow-файлы не менять. После установки обновить страницу для загрузки assets.

5. В браузере на staging выполнить 14 шагов ТЗ под инициатором, согласующим и закупщиком. Проверить обязательного руководителя, последовательность/минимум, мобильную форму, расширения Studio, двух клиентов, компании и отрицательные RPC-попытки. Не менять пароли и не расширять роли ради успешного результата.

Переносимые проверки:

```sh
python -m unittest discover -s extra-addons/approvals_purchase_vataga/tests/portable -v
node extra-addons/approvals_purchase_vataga/tests/portable/test_url_policy.mjs
python extra-addons/approvals_purchase_vataga/scripts/validate_local.py --odoo-source /path/to/odoo17
```

Для дополнительных portable contract-тестов нужен реальный Python runtime Odoo 17; если он не установлен как пакет, задать `VATAGA_ODOO_SOURCE=/path/to/odoo17`. Без него contract-suite явно пропускается. QUnit-тест readonly-таблицы добавлен в `web.qunit_suite_tests`; локально проверен его синтаксис, браузерное исполнение еще требуется.

`scripts/test_lock_protocol.py` предназначен только для отдельного локального PostgreSQL на `127.0.0.1:55491`. Он проверяет реальный SQL метода блокировки в собственном временном schema, затем удаляет только созданный им schema. Если Odoo не установлен как Python-пакет, нужно передать `--odoo-source /path/to/odoo17`; подключение задается через `--dsn`. Это **не** прогон Enterprise RFQ.

## Консервативные ограничения

- Переходы категории между закупочным и другим типом либо между различными способами нумерации требуют новой заявки. После отправки смена категории запрещена. Тип/способ нумерации категории с существующими закупочными заявками изменить нельзя.
- Строку закупочной заявки нельзя переносить в другую заявку, в том числе в черновике.
- Уже утвержденные строки остаются защищенными после отмены и возврата в черновик. Старые отмененные заявки с неизвестной историей при таком возврате получают отдельный консервативный lock, без утверждения, что они были согласованы.
- Старую согласованную строку без подтвержденного снимка нельзя заполнять как «исходно отсутствовавший товар». Для неоднозначной старой заявки следует создать новую; недостоверная история не восстанавливается.
- Фактические Enterprise/ERP-UA реализации workflow, поставщиков и compute-hook, UI после установки и все ролевые ORM/RPC-сценарии требуют выполнения отмеченных `BLOCKED` проверок.
