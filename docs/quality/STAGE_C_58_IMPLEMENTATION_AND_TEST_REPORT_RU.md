## 1. Реальные полномочия

| Участник | Разрешённое действие |
|---|---|
| Quality Manager | Назначить активного внутреннего мастера и складского исполнителя с уже имеющимися нужными ролями и компанией; указать причину. Отозвать невыполненное обычное решение с причиной перед новым назначением/подтверждением |
| Назначенный мастер с `group_quality_production_master` | Самостоятельно подтвердить обычный `scrap` или заявку D; вручную передать критический случай техсовету с причиной |
| Назначенный исполнитель с `group_quality_production_executor` **и Stock User** | Отдельно выполнить подтверждённое обычное решение своего случая по неизменному scope |
| Назначенный техсовет | Утвердить критический случай и самому исполнить при наличии Stock User, по прежним ограничениям |

Для обычного решения **UID мастера и исполнителя должны различаться** при назначении, подтверждении и исполнении. Даже наличие обеих ролей у одного пользователя не позволяет исполнить его собственное решение в данном случае. Совмещение групп в разных случаях не запрещается.

Созданы две **пустые** группы без `users`, `implied_ids`, наследования Quality Manager/техсовета/Stock/MRP и без назначения существующим сотрудникам. Выбор пользователя в документе не выдаёт ему роль. В отдельной локальной базе после прогона обе группы имеют **0 пользователей и 0 implied-групп**.

Новые ACL дают мастеру доступ к назначенному C Alert и необходимым данным; исполнителю — чтение назначенного Alert и связанные данные, без общего права его редактирования. Его складское действие проверяется отдельным серверным методом. Ограничения отдельно учитывают реальные прежние ACL чтения и записи, включая пользовательские группы ERP-UA, без замены их record rules. В тестах проверено, что добавление узкой роли не отнимает прежний MRP/read-only доступ и не расширяет read-only роль до общей записи; чужое действие не становится доступным только из-за новой роли.

## 2. Решение, исполнение и история

В `production_case_authority.py` добавлен явный маршрут `unclassified / ordinary / board`, назначения, отдельные действия подтверждения/исполнения, отзыв невыполненного обычного решения и неизменяемая история `quality.production.case.decision` без отдельного рабочего реестра.

История хранит события назначения, подтверждения, отзыва и эскалации: актёр, время, причина, маршрут, мастер, исполнитель, распределение и scope. Версия решения представлена отдельной неизменяемой записью с собственным ID; отзыв ссылается на исходную запись, повторное подтверждение создаёт новую. Операция фактической обработки связана с конкретным подтверждённым решением.

Обычное подтверждение **не устанавливает** `is_approved`, `approved_by_id` и другие поля утверждения техсовета. После передачи в критический маршрут обычные действия запрещены сервером. Прямое создание/редактирование маршрута, подтверждения или истории через RPC/default context не заменяет проверенную операцию.

Сериализация выполняется по MO → Alert → подтверждённому решению/остатку → quants. Проверяются компания, текущая роль, активность и внутренний тип пользователя, назначение, неизменность решения и отсутствие прежнего исполнения. Для ограниченного складского исполнителя не требуется общее Alert.write: повышенно читаются только проверенные метаданные/записывается аудит после проверки его действия. **Stock проводится в исходном окружении самого исполнителя.**

Матрица, история образцов, PASS/FAIL, B1, `production_release*.py`, чистая модель остатка и `production_residual_stock.py` не изменены. Общий C-обработчик выделен для двух маршрутов; записи служебного аудита и сообщения не дают складскому пользователю полномочий техсовета. Годные 3 не перемещаются повторно, списываются только доказанные 2. Заявка D оставляет 2 в карантине, не создаёт unbuild и не возвращает компоненты.

## 3. Исправление P1 C-G01

Источник защищённого случая определяется по текущим и новым связям:

- `stock.scrap.production_id`, `workorder_id.production_id`, прямой ссылке на C Alert;
- связанным движениям и picking: production, raw-material production, workorder, защищённому исходному move;
- старым связям при снятии/подмене; ORM defaults после create.

Проверки повторяются при create/write, перед `action_validate()` / `do_scrap()`, при удалении и перепривязке. Дополнительно закрыта привязка дополнительного `stock.move` к защищённому scrap через create/write и проведение. Внутренний неприсылаемый RPC-токен сохранён.

Четыре новых интеграционных негативных теста проверяют WO-only и default WO, поздний write и противоречивые MO/WO, снятие связей, оба публичных метода проведения и добавление движения к защищённому scrap. Проверяется отсутствие проведения и сохранение Q=2 / Stock=3. Прежний локальный воспроизводитель обхода также переведён на ожидание отказа: **Stock=3→1 больше не происходит**.

Классификация не вводит запрет на все движения SKU: обычные операции без связи с защищённым C-процессом проходят. На настоящем Community MRP проверены стандартные non-C производство 5 → разборка 2 → остаток 3 и обычное списание.

## 4. Стандартный интерфейс

Используется существующая форма Quality Alert: назначенные мастер/исполнитель, причина назначения/отзыва, обычное решение, передача критического случая, отдельное исполнение и связанные записи истории. Видимость и readonly рассчитываются по состоянию и роли; серверные проверки обязательны независимо от кнопок.

Новые роли используют **существующие** действия и меню Quality Alert. При upgrade функция добавляет две пустые роли к ограниченным меню Alert и их предкам/действиям; существующие группы сохраняются, открытые меню остаются открытыми. Не добавлены новый JS, приложение или рабочий реестр. Добавление групп к меню не назначает их людям.

Отдельно исправлен риск интеграции: скрытая One2many-ссылка Alert в MO/распределении ограничена группами качества/C. Обычный MRP/Stock пользователь без Quality не должен получать ошибку ACL Quality Alert при чтении стандартного MO. Это проверено на уровне ORM/fields_get; полная форма EE ещё требует браузера.
