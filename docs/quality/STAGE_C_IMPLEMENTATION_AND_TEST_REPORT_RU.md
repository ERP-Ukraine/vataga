## 2. Что реализовано

### Автоматическое сповіщення про якість

`models/production_quality_case.py` расширяет существующее событие обработки QC/выпуска. После подтверждённого FAIL у нового C-MO автоматически создаётся один стандартный Quality Alert. Каноническая связь защищена SQL `UNIQUE(production_case_mo_id)` и сериализацией по MO.

Alert содержит MO, исходную QC, все обязательные связанные QC, операции, lot/serial, номера и ID образцов, результат, снимки измерений, первоначальные отклонения и время регистрации. Новый FAIL другой обязательной QC добавляется в тот же случай один раз. Повторный вызов и штатная кнопка Alert у QC возвращают существующий документ. Создание второго Alert с C-QC, копирование канонического Alert и подмена связей запрещены сервером. Для связи QC используется отдельная таблица `quality_production_case_check_rel`, чтобы не конфликтовать с входными Alert этапа A.

Исходные QC, их PASS/FAIL, даты контроля, образцы и snapshot распределения B не переписываются. Нет автоматического сопоставления порядковых номеров образцов между операциями.

### Подтверждённый остаток и списание

`production_residual_plan.py` строит scope исключительно из неизменяемого распределения B, фактических исходных строк и реально проведённого выпуска. Произвольного параметра «сколько списать» нет. Проверяются источник, товар, компания, lot/serial, целые изделия, соответствие фактического выпуска разрешённому и доказанный FAIL для всего остатка.

Для примера 5/3/2 scope содержит **2**, а не исходные 5. Для серийного учёта нужен точный подтверждённый serial и одна единица. При неоднозначной идентификации, незавершённых обязательных проверках, общем физическом ключе, собственнике или упаковке исполнение блокируется. Для нескольких партий нужны отдельные однозначные источники; если часть общего scope недоказана, решение целиком блокируется.

`production_residual_stock.py` повторно проверяет scope перед выполнением и блокирует quants. Фактическое количество должно совпадать с остатком без резерва, отрицательных quants, владельца и упаковки. Проверка строгая: **1,6 вместо 2 не округляется до достаточного остатка**. Контекст очищается от посторонних `default_*`; внутренний токен нельзя заменить RPC-значением `True`.

Стандартный `stock.scrap` проводится от имени складского исполнителя, без `sudo` для движения. Проверяются карантин, scrap destination, lot, количество и результат `done`. Связь scrap с MO ставится после проведения по существующему безопасному образцу, чтобы не пересчитать списание как изготовленное количество. Ранее проведённый выпуск 3 остаётся неизменным. При полном FAIL отменяется только оставшийся канонический draft release.

Каждое проведённое списание фиксируется в неизменяемом `quality.production.residual.operation` со связями Alert, распределение, исходная строка, стандартное списание, количество, пользователь, время и snapshot. SQL `UNIQUE(source_line_id)` запрещает повторную обработку одного источника. Повтор команды завершённого случая не создаёт новых движений. Утверждённый scope сравнивается с актуальным перед исполнением; сам факт утверждения не разрешает списать изменившийся остаток.

`production_case_stock_guards.py` блокирует прямые `stock.scrap` и `mrp.unbuild`, связанные с C-MO/случаем, включая стандартную форму MO, defaults контекста, публичные методы проведения и попытки снять существующую связь. Обычные несвязанные операции сохраняют прежнее поведение. Это не вводит запрет на нормальное дальнейшее использование уже выпущенных годных изделий.

### Заявка D, интерфейс и права

После утверждения «Розбирання» отдельное подтверждение записывает автора/дату заявки D и сообщение в истории. Изделия остаются в карантине; обработанное количество не увеличивается, `mrp.unbuild` и возврат компонентов на CAB/Запаси отсутствуют.

Использованы стандартные формы товара, MO, Alert и «Розподіл ВТК», smart button и связанные документы. В Alert показаны изготовлено, выпущено, осталось в карантине, списано, исходные QC и отдельный статус обработки. При незавершённой QC отображаются уже проведённые фактические 5/0/5, а не нулевые количества только из-за отсутствия распределения. Старые действия на исходную полную партию для C скрыты и заменены узким серверным маршрутом C. Новый JS, меню или самостоятельный рабочий реестр не добавлялись.

Добавлены только две read-only ACL и правило компании для аудита обработки. Группы техсовета, доступ мастера, назначение утверждающего и действующие ограничения A не изменялись. Код Shop Floor, регистрации выработки, расчёта B, матрицы и входного контроля не редактировался.

### Восемь C-проверок с настоящим Stock

1. Приход 5 → стандартный выпуск 3 → scrap 2 из карантина: Q=0, Stock=3, исходный приход=5, выпуск=3; повтор отклонён, новых движений нет. Контекст `default_quantity=99` не меняет количество.
2. Полный FAIL 5 с конкретной партией: scrap=5, Q=0, Stock=0, lot сохранён.
3. Попытка списать 5 вместо остатка 2 либо чужой lot: отказ; Q=2, Stock=3.
4. Scope=2 при фактическом Q=5: отказ без автоматического уменьшения или частичного выбора.
5. Недостаток 1, недостаток 1,6 и резерв 1 при утверждаемом остатке 2: отказ до создания scrap; Stock=3 сохранён.
6. Владелец или упаковка исходного изделия: отказ, новое списание не создано.
7. Две выбранные партии 2 и 1 списываются отдельными документами; третья партия 4 остаётся в карантине.
8. Бракованный serial списывается точно по своему номеру; другой serial уже выпущен и остаётся на складе в количестве 1.

Native source fixture — изолированное поступление в тестовый карантин, позволяющее проверить настоящий механизм Stock без Enterprise. Это **не** утверждение о полноценной проверке производства, автоматического Alert или технического совета в EE.

В native-регрессии A две конкурентные транзакции штатно вызывают `could not serialize access due to concurrent update`; Odoo повторяет транзакции, итоговые конкурентные тесты PASS. Эти ожидаемые сообщения SQL сохранены в полном логе и не являются ошибкой финального тестового результата. C-конкурентность этим прогоном не доказана.

## 5. Что осталось для приёмки staging

После восстановления браузера: опубликовать кандидат только в staging, выполнить upgrade модуля и проверить загрузку реестра/форм. Если обнаружатся ошибки EE-интеграции, исправить их и повторить соответствующие проверки. Пока развёртывание и успешный upgrade не заявляются.

Создать отдельные AQC-C-* товары, MO, партии/serial и QC, явно включив B+C только на новых тестовых товарах CAB. Пройти C01–C21 из GAP: автоматический Alert при 3 PASS / 2 FAIL и полном FAIL, ожидание незавершённых образцов, несколько QC и партий, повторные и конкурентные действия, мастер и назначенный/чужой техсовет, отсутствие складских прав, списание из карантина, заявка D, подмена RPC/context/source/lot/количества. Проверить реальные quants, исходные 5, done release 3, scrap 2, канонический Alert, полный аудит и сохранение QC FAIL.

Проверить реальные переходы MO ↔ распределение ↔ Alert ↔ QC/образцы ↔ scrap/складские движения, затем новую регрессию входного контроля и Shop Floor. Эталон MO05300 / распределение13 / Alert67 использовать только для чтения. На production ничего не переносить до завершения отдельной приёмки.
