## 2. Нужна ли специальная миграция

| Изменение `.56 → .58` | Как устанавливается |
|---|---|
| C-поля в product/MO/Alert, связи распределения и scrap | Обычный ORM schema upgrade |
| `quality.production.residual.operation` и `quality.production.case.decision` | Новые пустые таблицы, индексы/связи/ограничения при upgrade |
| Канонический Alert, UNIQUE MO и источника обработки | Новые nullable связи/пустая таблица; при исходной `.56` чистить дубликаты нечего |
| Пустые роли мастера и исполнителя, ACL и условные record rules | Данные security XML; без автоматического назначения людям |
| Стандартные формы и доступ новых ролей к существующим Alert-меню | Обновление views и функция настройки только групп существующих меню/действий; открытые меню не сужаются |
| Старые MO и распределения | C выключен; snapshot B/образцы/остатки/история не изменяются и не пересчитываются |

Для подтверждённого исходного состояния **`.56` специальный SQL/data migration и backfill не требуются**. Не нужно устанавливать `.57` промежуточно, подключать старый MO05300 к C, сбрасывать QC или пересоздавать складские документы. Обычный upgrade обязателен из-за новых хранимых полей/моделей/прав.

`post_init_hook` модуля не менялся; стандартный Odoo вызывает его при установке, а не обычном upgrade. Единственная прежняя функция данных `set_param` для поля инвентарного номера оборудования остаётся прежней; новых функций, меняющих рабочие поступления, MO или quants, нет.

Если перед установкой окажется, что в базе уже есть другая версия C и активные C-решения, этот вывод о данных `.56` неприменим: сначала отдельно проверить такие записи и согласовать перенос их состояния. Автоматического перевода старых решений A в ordinary B или выдачи полномочий не предусмотрено.

## 3. Последовательность после отдельного согласования публикации

1. Уполномоченный администратор подтверждает домен **vataga-staging.erpu.cloud**, установленную `.56`, наличие резервной копии БД и filestore и способ восстановить связку БД/filestore/версии кода. Согласует короткое окно без работы пользователей в staging. Эталон MO05300 / QC00606 / распределение13 / Alert67 не проводить повторно.
2. До публикации открыть стандартный **Apps** в администраторской сессии staging. Не оставлять активным рабочий экран MO/QC. Новые колонки должны быть установлены до возобновления работы пользователей; обычные документы не открывать в промежутке «новый код / старая схема».
3. Опубликовать **полный кандидат `.58`** в `staging`, дождаться GitHub Actions → Deploy to Staging для этого commit и `running` соответствующего rebuild. Отдельно `.57` с P1 не публиковать. `main`/production не использовать.
4. Администратор выполняет ручные действия в Odoo, перечисленные ниже. Этот шаг **не заменяется** успехом Actions.
5. После успешного upgrade проверить установленную `.58`, отсутствие ошибок registry/SQL/XML/ACL, пустые новые группы и доступ обычного MRP-пользователя к стандартному MO. Только затем возобновлять работу пользователей staging.
6. На отдельных AQC-C-* документах и отдельных тестовых ролях выполнить фактическую приёмку: обычное решение разными людьми, критический совет, 5/3/2, повтор, pending, партии/serial, C-G01, D без движения и регрессию A/B/Shop Floor. Browser PASS ставится только после проверки интерфейса и реальных движений.

При ошибке upgrade не продолжать работу со складскими документами и не выполнять ручные SQL-исправления остатков/решений. Сохранить traceback и определить, откатилась ли транзакция upgrade. При необходимости восстановить согласованную резервную копию вместе с совместимым кодом; простой откат образа после изменения схемы не считать полным восстановлением. Автоматический rollback здесь не запускается.

## 4. Что потребуется вручную в Odoo

Выполняет администратор с доступом к управлению модулями; роль координатора Quality Manager сама по себе не заменяет эти права.

1. Войти в **staging**, открыть **Apps / Застосунки**. При необходимости включить режим разработчика для команды обновления.
2. Убрать стандартный фильтр **Apps**, поскольку `quality_vataga` не является отдельным приложением. Найти технический модуль `quality_vataga` (название «Параметри якості обладнання Vataga»).
3. После rebuild обновить список приложений, если карточка не видит новый manifest. Открыть карточку модуля и выбрать **Upgrade / Оновити**. **Не выбирать Uninstall / Видалити и не обновлять все модули.**
4. Дождаться завершения перезагрузки и проверить **установленную**, а не только доступную версию: `17.0.2.58`.
5. В настройках групп проверить наличие «Виробничий брак C: рішення майстра» и «Виробничий брак C: складський виконавець». Они должны быть без автоматически добавленных сотрудников и без implied Quality Manager/board/Stock/MRP.
6. Группы конкретным людям назначать только отдельно и явно. Для теста нужны разные внутренние пользователи мастера и склада; у склада дополнительно должен уже быть Stock User. В карточке нового тестового Alert координатор Quality Manager выбирает этих участников и вводит причину. Сам выбор участника не выдаёт группу.
7. C включать лишь на **новых явно включённых тестовых товарах CAB с B+C** и новых MO. Старые рабочие товары/MO и эталон не подключать.

Если после rebuild стандартный Apps экран не открывается из-за несовпадения кода/схемы, не пробовать проводить документы: требуется штатный серверный upgrade через поддерживаемый канал ERP-UA либо восстановление согласованной связки. Автообновление SaaS до подтверждения не предполагать.
